# Capabilities and known limitations

User-facing status of the features reviewed in wave 11. Only claims that were verified by the reviewers are listed as capabilities; everything else is a known limit. Numbers come from the reviewers' own runs (Apple M2 Pro, 16 GB, Homebrew ffmpeg 8.1.1) unless stated otherwise.

## Status at desktop 1.0.0

Release notes: [releases/v1.0.0.md](releases/v1.0.0.md). Gap status against Premiere: [PREMIERE-GAPS.md](PREMIERE-GAPS.md). Sections below were written wave by wave; where a later wave changed a limit, the section says so or this list does.

Open at 1.0.0:

- **Real-time collaboration is experimental and deferred.** Its end-to-end test fails and nothing is deployed. See the Real-time collaboration section.
- **Interchange (XMEML, FCPXML, EDL, OTIO, AAF) has not been opened in Premiere Pro, Resolve, Avid or Final Cut.**
- **Desktop cold start is about 1.0 s to an open editor on macOS, measured on a busy machine only.** Spawn to editor interactive (clicking the instant the welcome screen shows) was 994 ms median against 1088 ms for the previous build in interleaved runs at load 4-8; no idle-machine number exists yet, the new 1100 ms budget is untested on one, and the audio start-up warm-up (a hidden frame process plus `AudioServiceLaunchOnStartup`) was not measured on Windows or Linux. A user who clicks after the welcome screen has settled sees no difference. See `apps/desktop/PERF.md`, "Cold start round 3".
- **Sequence pixel aspect ratio is applied to titles, shapes, SVG, stickers, captions and particles** in export, the Program monitor and template thumbnails, like video. The WebGPU compositor now rotates, scales and positions each layer in display space and squeezes it to stored pixels (the same math as Canvas2D and export), so a rotated layer is not sheared in a non-square-PAR sequence, and blur-like effects on overlays (their own effects in export) and on adjustment layers run on a display-space (stored width x PAR) copy of the pixels, so they are isotropic when displayed, in the Program monitor, the Canvas2D fallback and export. Blur on a video clip's own effects is also isotropic in the Program monitor: a CSS-filterable clip (blur, brightness and so on) is filtered in a display-space layer that is then squeezed, instead of under the 1/PAR squeeze (where `ctx.filter` radii stay in device pixels and were anisotropic by the PAR); export blurs the decoded frame before layout. Remaining gaps: in a PAR below 1 (DV NTSC 0.9091) the display-space copy is narrower than the stored frame, so an overlay or adjustment layer that has effects loses a little horizontal sharpness (the copy is made even for colour-only effects); the Program monitor does not render effects on titles and shapes at all (export does), so monitor and export agreement for an overlay's own blur is not testable and only export is measured; the monitor's CSS blur and export's effects-engine blur differ in kernel by about 23% in spread even at square pixels (not PAR related). Field order and pixel aspect on footage are applied in preview, thumbnails and export.
- **Wall-clock performance budgets were not judged on an idle machine.** CPU and memory budgets pass. Measured seek p95 is about 16 ms, 4K scrub p95 about 90 to 100 ms and dropped frames under 1%, all on a loaded Apple M2 Pro. See `apps/desktop/PERF.md`.
- **Two-pass VBR** is desktop-only (ffmpeg), and unavailable for AV1, fixed-rate codecs and Rec.2020 projects.
- Windows and Linux builds ship, but performance and the native decode paths were qualified on macOS.

Superseded by later waves (the older text below is left for history):

- ProRes: projects reopened from storage now reopen with native decode, and rotation metadata is honoured (wave 14). The "Projects reopened from storage" and "rotation metadata is ignored" lines under ProRes no longer apply.
- Memory: the governor's decoder estimate was recalibrated (120 bytes per source pixel, about 249 MB for a 4K decoder, `DECODER_BYTES_PER_PIXEL`) and a hard 4K memory gate was added, so the "149 MB estimate" and "does not degrade it in time" lines are out of date. The 3.7 to 4.0 GB figure for two overlapping 4K layers from whole 10-minute sources was not re-measured.
- LUTs: the `.cube` parser now reads 1D and 3D tables with their domain and keeps float data, and LUTs carry through render and persistence.
- Export presets can be saved, imported and managed from the Export dialog.
- Effect keyframes are keyed by effect instance (`fx:<id>:<param>`) and older type-keyed keyframes are rewritten on load.

Limits that remain:

- Projects reopened from storage: media reloaded from IndexedDB has no disk path, so native decode does not claim it. Relink or re-import the file.
- Constant frame rate is assumed; rotation metadata is ignored.
- Audio from a ProRes `.mov` through the native path is unverified.

- The sidecar manifest ffmpeg builds (6.1.1 x64, 7.1 arm64) were not exercised; only Homebrew ffmpeg.

## Multicam speed and reverse

Shipped and verified in a real browser: multicam clips can be retimed (constant speed and reverse). Picture and audio stay locked.

- 2x speed: 6 claps, peak audio/picture error between -0.2 and 1.8 ms.
- Reverse: 5 claps, peak error up to 4.7 ms.
- A randomised test (400 sequences, about 9,580 samples) confirms audio and picture share time.

Limits that remain:

- Speed ramps and freeze frames on multicam clips are covered by unit tests only (no e2e or export check), and cuts inside a ramped or frozen multicam clip are refused.
- Neighbouring clips at different speeds do not merge their audio into one clip.
- Multi-clip ripple speed exists for ordinary clips (Clip > Speed/Duration, see "Multi-clip speed and ripple" below); a multicam clip with speed ramps or freeze frames is still refused.
- The Canvas2D fallback variant was not verified. XMEML multiclip round trips retimed multicam cuts in unit tests; FCPXML `mc-clip` and OTIO (which flattens multicam) were not checked with retimed cuts, and none of it was opened in Premiere Pro, Resolve or Final Cut.
- Other multicam limits: see [multicam-editing.md](multicam-editing.md). The older line "angles must play at normal speed to be switched" is superseded by the above for constant speed and reverse.

## Smart render

Guarantees (desktop native path and browser planner, shared planning code):

- Untouched, grid-aligned spans are stream-copied; touched spans are re-encoded. A copy happens only when the frame-grid test proves it identical.
- If a source file is changed or truncated while being hashed or exported, export fails or re-encodes instead of copying stale data.
- Verified: a one-byte edit in the middle of a file is detected; a 45 s source with a 1.4 s start offset copied 93% (1587 ms vs 5576 ms full re-encode, 1290 frames identical to the source); a 90 s timeline copied 98% (1307 ms vs 9587 ms). Worst PSNR of the smart output vs a full re-encode was 46.4 dB.
- Anything with effects, grading, transforms, speed, transitions, text over it and so on is always re-rendered. See `apps/desktop/SMART_RENDER.md`.
- Audio (desktop native path): when the mix is exactly one untouched source the audio is copied instead of mixed and encoded. AAC-LC packets are copied for the whole export when the cut points sit on the source's 1024-sample frame grid (a cut inside the stream carries one pre-roll frame and is proved against the source's decode first; any other cut is re-encoded); untouched spans of 16/24-bit PCM sources are copied sample for sample into ProRes MOV masters. AAC is never spliced with rendered AAC, mono / 5.1 / other sample rates / HE-AAC / MP3 are re-encoded, and a source whose AAC uses noise substitution is copied only from its first sample. The export report and queue row say how many seconds of audio were copied.

Limits that remain:

- Hashing cost was measured warm (about 0.5 s/GiB Node, 0.7 s/GiB Chrome). Cold-disk cost is unmeasured and I/O bound. The first export of a large never-hashed file may wait for the remaining hash.
- The grid tolerance (0.02 frame, or 0.6 ms) is an engineering choice.
- The native Electron copy path was exercised through real-ffmpeg integration tests, not through the full Electron app. Only Homebrew ffmpeg 8.1.1 was tested, not the sidecar 7.1 and 6.1.1 builds.

## Memory

Status after w17: the import-time peak of long 4K sources is fixed (about 1.5 GB lower), a global memory governor now degrades the preview instead of letting caches and decoders grow, and a playback freeze that turned out to be a playback restart is fixed. The 5.6 to 6.6 GB renderer peak of the 110-minute soak was **not reproduced** (highest peak seen in any run: 4.7 GB total, with tracing overhead), and the layered 4K case with two overlapping 4K layers from 10-minute sources still peaks at 3.7 to 4.0 GB. Details and what is not done are below.

### Reproduction

`apps/web/e2e/soak/memory-4k-layered.spec.ts` (`pnpm --filter @openreel/web test:memory-gate`, `test:memory-gate:long`): three real 4K long-GOP cuts (H.264, HEVC, H.264; stream-copied from the soak sources, 10 s keyframes) on three video tracks, imported with 540p proxy creation. It scrubs at random, plays 40 s layered, toggles proxies on and off six times while playing, scrubs on proxies and originals, plays 30 s more, and forces the memory governor to critical and back. `SOAK_4K_SECONDS` sets the source length: 90 s (default, proxies) or 600 s (`test:memory-gate:long`, no proxies). `playback-4k-memory.spec.ts` (`SOAK_4K_FULL=1 SOAK_4K_LAYERED=1`) is the older shape: four distinct whole 10-minute sources back to back plus one overlapping layer.

Instrumentation (all opt-in, `apps/web/e2e/soak/soak-lib.ts`): process-tree RSS split by renderer, GPU and other every second; macOS `footprint` of the renderer; Chrome memory-infra dumps through CDP (`SOAK_4K_MEMINFRA=1`: partition_alloc, blink, v8, gpu, iosurface, shared images per process); page counters (open VideoFrames, ImageBitmaps, decoders, JS heap, `SOAK_4K_TIMELINE=1`); every `Blob.arrayBuffer()` call site with its bytes (`SOAK_4K_TRACE_AB=1`); console warnings and errors; playback lifecycle events; project changes while playing. `e2e/soak/probe-memory-signals.mjs` shows which page-visible memory signals see which allocations.

### What changed

- Import: the ffmpeg.wasm audio-stream probe is skipped for files above 64 MB when mediabunny already counted the audio tracks (`shouldProbeAudioStreamsWithFfmpeg`); below 64 MB the second opinion is kept. Import-phase peak for three 10-minute sources: 2.5 to 2.9 GB to 1.40 to 1.42 GB.
- Audio decode (`decodeAudioBufferStreaming`) copies each decoded `AudioSample` straight into the output buffer and closes it, instead of allocating an AudioBuffer per packet for the garbage collector. Its effect on the peak could not be separated from noise.
- Memory governor (`packages/core/src/device/memory-governor.ts`, `useMemoryPolicy`): estimates renderer memory as max(`performance.memory`, `measureUserAgentSpecificMemory` every 20 s) plus the frame caches plus the open decoders (4K long-GOP decoder estimated at 12 NV12 frames, 149 MB), against a limit of 30 % of system RAM clamped to 1 to 3 GB (2.4 GB when the browser reports its 8 GB cap). Above 65 % of the limit: caches at 60 %, Program monitor resolution x0.75, two decoder elements. Above 90 %: caches at 30 %, resolution x0.5, one decoder element, no read-ahead audio decode. Hysteresis 50 % / 75 % on the way back. The caches follow through the shared media budget (`getMediaMemoryBudget` times the policy scale), so no cache knows about the governor. A "Memory high" or "Low memory: reduced preview" badge shows next to the proxy toggle; exports are not affected. Registered: decoded audio, scrub frames, bitmaps, VideoEngine frame cache, VideoEngine decoder elements, every MediaBunny layer decoder during multi-track playback.
- Playback no longer restarts when a waveform finishes (`playback-project.ts`, see below).
- Frame decodes during multi-track playback have a 4 s deadline (`decode-deadline.ts`): a decoder that stops answering costs its layer for a moment and is rebuilt, instead of blocking the loop. A watchdog (`playback-watchdog.ts`) restarts a frame loop whose frame has not ended after 5 s and records where it was waiting. Neither fired in any run after the fix below.

### Playback freeze

One layered playback in w16 advanced 16 s of 46 s. It reproduced here on the build without any w17 change (playhead stuck at 17.13 s for the remaining 28 s, no console message), and on 9 of 9 runs on pre-fix builds that had memory-infra tracing on (stuck at 23 to 26 s for 20 s; the one traced run that also forced garbage collections through the diagnostics did not), because tracing slows the renderer enough for the trigger to fire. Untraced it was rare: 1 of 17 pre-fix four-source runs (plus the w16 report). The playback events log shows the cause: the playback effect depends on `project`, and a waveform finishing in the background writes `waveformData` into the media library, a new project identity. Each write tore playback down (clock paused, decoders closed) and restarted it, once at about 7.6 s, 11.1 s, 24.6 s and 25.1 s of the run. Every restart cost a 0.7 to 1 s hitch (the "maxFlat 750 ms" at 7 to 9 s in every run since w16), and the one at 24.6 s took the single-clip native path, which never reached "started" (no `native-started` or `multi-start` event after `effect-start`), so the playhead stayed frozen. `useStablePlaybackProject` keeps the project identity while only `waveformData`, `thumbnailUrl` and `filmstripThumbnails` change (and `sameProjectForPlayback` replaces the two identity checks in the paused-frame commit and the compound audio preview). After it: 0 of 6 traced runs froze (advanced 45.3 to 45.6 s of 46 s) and the events log of each shows a single effect start, 0 of 6 untraced four-source runs and 0 of 8 gate runs. A hitch of 0.75 to 1.25 s at 7 to 9 s of the four-source case remains and is not explained (it is no longer a restart).

### Gate

`memory-4k-layered.spec.ts` fails when the total RSS peak is above 3072 MB (the highest measurement of the fixed build, 2552 MB, plus about 20 %; the target is 4 GB), when the import phase of 600 s sources is above 2048 MB (the unfixed build measured 2527 to 2913 MB, so it fails; the fixed build measures 1.4 GB), when the playhead is flat for 3 s or playback advances less than 90 % of wall time, or when forcing critical pressure does not shrink the Program canvas, show the badge, and recover. `playback-4k-memory.spec.ts` keeps its own gates (2560 MB for short cuts, 4608 MB for whole 10-minute layered). `scrub-smoke.spec.ts` checks that seeking repaints the monitor on the fixture and, with `SOAK_SMOKE_4K=1`, on a 4K cut (it caught a regression in the first version of the playback project change: the paused-frame commit compared project identities).

### Not done and limits

- The four-source shape (two simultaneous 4K layers decoded from whole 10-minute sources) still peaks at 3.7 to 4.0 GB, and the memory inside the renderer during that spike is not attributed: JS counters are balanced, memory-infra cannot dump the renderer while it spikes. The governor's decoder estimate (149 MB per 4K decoder) is far below what this case shows, so the governor does not degrade it in time.
- The 5.6 to 6.6 GB peak was not reproduced. The long soak (800 clips, 110 minutes) was not rerun.
- Whole-file decoded audio remains: 230 MB per 10 minutes of stereo per source. There is no windowed audio decode.
- Web proxy creation (ffmpeg.wasm, "Create proxies" ingest) still copies the whole source into WebAssembly memory.
- The governor does not turn proxies on by itself and does not limit decoders for fully occluded layers. Its numbers (30 % of RAM, thresholds, 12-frame decoder estimate) are engineering choices tuned on one 16 GB Mac. On desktop it sees the renderer only (no main or GPU process metrics). Not tried on 8 GB machines, Windows or Linux.
- A restart of playback mid-play (any real edit) can still hit the native-start hang that froze the soak; its location is recorded (events log) but the cause is not fixed. The 5 s watchdog only covers the multi-track frame loop.
- `VideoEngine.setMaxVideoElements` and the Preview wiring of the governor have no unit test; they are covered by the gate spec only.
- Desktop: the Electron `memory4k` row did not move (12 s clips, one 4K layer at a time): 1628, 1631, 1637 MB before and 1642, 1670, 1613 MB after. The overlapping-layers and 10-minute-source shapes were not run on desktop.

Hardware needed (unchanged): 8 GB RAM minimum for HD editing; 16 GB or more for 4K long-GOP. The 3 GB desktop budget (`perf-budgets.json`) is a regression guard on a light fixture.

## Export frame rate different from the sequence frame rate

The preview always plays at the project (sequence) frame rate. When Export settings use another rate, the sequence is rendered at its own rate and conformed, as in Premiere: export frame N (stamped N / export fps) shows the sequence frame that is on screen at that instant, the same frame the preview shows for that playhead. A 24 fps sequence exported at 30 fps repeats one frame in four; at 12 fps every other frame is skipped. Keyframes, transitions and effects are never evaluated between two sequence frames and the sequence's own frames are not blended or optical-flowed to the export rate (Premiere's default is the same hold; per-clip Time Interpolation, below, only fills in source frames inside a clip). Source clips with their own frame rate are still sampled by the sequence frame, not by their native frames. With equal rates nothing changes. `exportRenderTime` (`packages/core/src/video/frame-time.ts`) is the one rule, covered by unit tests and an export-engine test of the instants rendered. Smart render and Use previews (render cache) only apply when the rates match.

## Custom transitions

- **Canvas2D only, no WebGPU transition path.** Every transition renders through the Canvas2D `TransitionEngine`; the WebGPU compositor never had transition shaders and this work did not add them (the PREMIERE-GAPS "WebGPU effects and transition coverage" item stays open), so nothing here is checked on a WebGPU renderer. The editor preview calls the engine through `TransitionBridge` (at its own 1920 x 1080 size) and the export through `VideoEngine` (at the export size); border width is stored in project-frame pixels and scaled to each. The e2e compares the engine with a pure reference (94 frames, mean difference under 0.5 grey levels) and a preview frame with exported frames: the preview shows a frame about half a frame earlier than the exported frame at the same playhead, so the closest exported frame (59 or 60 of the test) differed by 11 grey levels per cell on a 16 x 9 grid (the strip moves about 15 px per frame), not zero.
- **Mask edges are built at most 960 px wide.** Iris, band, barn door, clock and gradient wipes are rasterised as a mask (at most 960 px wide) and scaled to the frame, so on a 1080p export a hard edge is softened over about two pixels. At 1080p the mean difference from a full-resolution reference was 0.3 grey levels in the e2e; the largest single-pixel differences are on edges. Border width is in output pixels.
- **Gradient Wipe image.** A picked image is reduced to a 64 x 36 luma map (stored base64 on the transition, about 3 KB) and sampled bilinearly, so fine detail in the image is lost and the wipe edge follows a smooth version of it. Dark areas reveal first, like Premiere; the map is stretched to its own darkest and brightest value so the wipe always completes.
- **Cube Spin is a perspective cube, with fixed camera and background.** Since the second transitions round it is a real projection (`transition-plans.ts`): two faces of a cube turned about its centre, drawn column by column (row by row for up / down) so the perspective is exact, with the cube pulled back so the near edge keeps the frame's height, culling of a face that has turned away, and an optional Border (outline of the visible faces). The camera distance (3 cube widths), the pull-back and the black background are fixed: no lighting, no shading of the far face, no camera or background colour parameter. The far corners of the outgoing face swing a few percent past the frame edge half way and are cropped. Film Dissolve is a linear-light mix at the frame's 8-bit values (a per-pixel pass, slower than a plain dissolve at 4K); in the float HDR path it is not a float transition and falls back to the 8-bit path like the other non-dissolve transitions. Additive Dissolve is "both shots at full strength at the midpoint", not Premiere's exact curve.
- **Start / End percentage and Reverse.** Start / End applies to every transition (it maps the eased progress). Feather, Border and Reverse apply only to the iris, band, barn door, clock and gradient wipes; Reverse is not offered for the older transitions. Alignment keeps working as before and Start / End is not shown on the timeline.
- **Project presets and the app-wide library.** Saved transition presets live in the project file (they travel with it); "Save to library" in the inspector keeps a preset in the app-wide library instead, in this browser profile's (or the desktop app's) IndexedDB, with Export presets / Import presets as a small JSON file (`openreel-transition-presets`, version 1). Names are unique per list (case-insensitive); a library preset and a project preset may share a name. The library is not synced between machines or browsers (clearing site data deletes it; export first), and when storage is unavailable (a private window, blocked IndexedDB) saving to it fails with a message instead of keeping it in memory. A project never needs the library: applying a preset copies its type, duration and parameters onto the transition, and a default transition set from a library preset stores the same values with `scope: "global"`, so on a machine without that preset it still applies unchanged and the panel shows "preset not found, using saved settings". Importing skips entries with an unknown transition type (a file from a newer build) and numbers clashing names ("Name (2)"); a file over 2 MB or with more than 500 presets is cut or refused. Agent tools can save to, list, delete from, export and import the library only in the live editor (the headless host has no per-user storage).
- **Cmd/Ctrl+D.** In the default OpenReel shortcut set Cmd/Ctrl+D is still Duplicate; Apply Default Transition is Shift+Cmd/Ctrl+D. The Premiere shortcut set binds Cmd/Ctrl+D to Apply Default Transition and moves Duplicate to Alt+Cmd/Ctrl+D. Apply Default Transition works on a selected clip (its next cut, else its previous cut, else an outro), two selected adjacent clips, or the cut at the playhead on an unlocked video track; it does not apply to audio (there is no default audio transition setting).
- **Interchange.** Transitions with a Premiere name are written under it: xmeml (Premiere / FCP7 XML) writes `<effectid>` and `<effectcategory>` from the table in `interchange/transition-names.ts` (Film Dissolve, Additive Dissolve, Iris Round / Box / Cross / Diamond, Band Wipe, Barn Doors, Clock Wipe, Gradient Wipe, Radial Wipe, Venetian Blinds, Checkerboard, Checker Wipe, Inset, Wedge Wipe, Random Blocks, Random Wipe, Split, Cube Spin, Flip Over, Cross Zoom, Page Peel, Page Turn) and reads those names back as the same OpenReel type with default settings; OTIO writes a Custom_Transition with that name and keeps the exact type and `alignment` in OpenReel's metadata, so OpenReel to OpenReel is lossless. The settings (direction, corner, border, feather, seed...) are not carried by xmeml: the export report lists a transition with non-default settings as approximated. **These names were NOT opened in Premiere Pro or DaVinci Resolve here** (there is no Premiere install in this environment); whether either resolves each name to its own built-in transition is unverified, and a name they do not know imports as a cross dissolve there. FCPXML, EDL and AAF write a cross dissolve and the report names the transition and, for FCPXML, the closest Final Cut transition to apply by hand (FCPXML matches transitions by Final Cut's own effect ids, which are not written; the EDL also notes the Premiere name in an `* EFFECT NAME:` comment). Transitions with no Premiere equivalent (Glitch Cut, Ripple, Color Split, Pixelate...) are still a cross dissolve and approximated in every format. An older build reads a project saved with a new type as a cross dissolve.
- **Not done:** Cross Zoom, Page Peel (Page Turn exists, but is the older approximation), Checkerboard and other wipes not listed above.

### More transitions (second round)

- **Not compared with Premiere.** Cross Zoom, Page Peel, Checkerboard, Checker Wipe, Inset, Split, Wedge Wipe, Random Blocks, Random Wipe, Flip Over and the new Cube Spin follow Premiere's transitions of those names in intent and parameters (direction / orientation / corner, border, feather, reverse, start / end where they apply); nobody laid a frame of them beside Premiere's, so timing, easing, zoom amounts and patterns are our own. The Radial Wipe that already existed is a centred sweep (Clock Wipe is the same with feather and border), not Premiere's corner pivot; set the Clock Wipe's centre to a corner for that look. Page Turn is the flat compress it was.
- **Page Peel is a flat fold.** The page folds along a line moving from the chosen corner and the lifted flap is drawn reflected, lightened as the back of a sheet, with a soft gradient shadow (Fold shadow); there is no curl or rolled cylinder, no lighting on the flap and no page thickness. The shadow is drawn by the canvas only and is not in the software reference the tests use.
- **Cross Zoom** zooms the outgoing shot in about 2.5x and the incoming one settles from the same zoom, averaging 12 zoom samples as the blur; it is a zoom blur, not a radial motion blur, and the amount is `intensity` (0 to 3). Cost is 24 full-frame draws per frame at the centre of the transition.
- **Checkerboard and Checker Wipe.** Checkerboard opens one colour of squares from their centres, then the other (Premiere slides them in); Checker Wipe sweeps each square in the chosen direction, alternating squares in opposite ways. Squares are square (the columns setting fixes their size), the grid starts at the top left and the last row or column is cut off by the frame.
- **Random Blocks and Random Wipe** use a seed (0 to 999999, default 1) saved on the transition, so preview, export and any other machine draw the same pattern (integer hash, pinned by tests). The pattern is ours, not Premiere's, and "New pattern" picks a random seed in the UI (the seed is then stored). Border colour on these paints whole blocks or strips just before they open.
- **Split** slides the outgoing halves apart over the incoming shot (Reverse slides the incoming halves in over the outgoing one); Border draws a strip on the inner edge of each half. **Flip Over** turns the shot like a card in perspective, outgoing on the front and incoming on the back, over black; Border outlines the card. Neither takes feather. Cube Spin, Flip Over and Split borders are in project-frame pixels and scale with the render size like the mask borders.
- **Cost.** Cube Spin and Flip Over draw one image slice per screen column (up to 1920 draws a frame at 1080p, 3840 at 4K); not benchmarked at 4K export beyond the browser parity test.
- **Cards.** The card list reports `hasDirection` for the new types from their parameters (`direction` for Cube Spin, Flip Over, Checker Wipe, Random Wipe; `orientation` or `corner` for the others). The older Spin and Flip cards were not re-audited.
- **Checks that ran.** Unit: pixel and geometry tests (`transition-plans.test.ts`: every direction at 0, 0.25, 0.5, 0.75, 1, vanishing point, faces never inverting; `transition-masks-2.test.ts`; `interchange/transition-interchange.test.ts`), the preset library on fake-indexeddb, the agent tools. Browser: `e2e/transitions-2.spec.ts` compares the real engine with the reference for 185 frames (masks within 0.35 grey levels, geometric plans within 1.6 mean; a one-pixel edge differs by up to 180 at most) and saves a Split with a white border to the library, reloads, applies it from the Presets filter, undoes, redoes and exports: the preview at frames 58 to 62 and at the half-frame playhead equals the exported frame of the same index (mean cell difference under 1 grey level, the next best frame 6 worse). It uses Split rather than Cube Spin because Cube Spin's edge moves too slowly per frame for a 16 x 9 grid to tell neighbouring frames apart; the first version of that test also showed that decoding the export through ffmpeg's area scaler smears a thin chroma edge into the next cell (the older `exportGrid` helper still does that), so the new spec decodes the frame at full size and averages it itself. No WebGPU path, no Premiere / Resolve / Final Cut import of the written files.

## Basic Correction, Auto Tone and Match Color

Basic Correction (exposure, contrast, highlights, shadows, whites, blacks) is one 256-entry tone curve and the vignette is a radial multiply. Both run in the fused CPU grading stage (after the colour wheels, before curves, LUT and HSL), so the WebGL2 preview, the Canvas2D fallback and export use identical code; they are not in the WebGL2 wheels shader.

Limits that remain:

- On clips using the classic processing order (every clip graded before the Premiere-order pipeline existed), tone and vignette are 8-bit per channel and apply after the colour wheels. Switch such a clip to Premiere order (Color tab, Processing order) for Basic Correction first in float; see the next section.
- Shadows and Highlights have deliberately bounded reach (about 0.15 of full scale at the slider extremes, within the lower and upper halves of the range) to keep the curve monotonic.
- Auto Tone and Match Color measure the Program monitor frame: Match Color reads the reference with its grade and the target ungraded, and it replaces the wheels and the Contrast slider and adds saturation to every HSL band. Curves, LUT and keyframed values on the target are kept, so the result is closest when those are neutral. Overlapping video layers contaminate the measurement.
- The Match Color reference is a frame of another timeline clip (the playhead frame when it is over that clip, otherwise its middle). There is no click-to-pick on the timeline yet.
- Basic Correction keyframes are sampled per frame in the preview and export (unit-tested); the e2e specs do not exercise keyframed tone in an export.

## Essential Sound panel

Shipped and verified in a real browser (`apps/web/e2e/essential-sound.spec.ts`): tag a clip as Dialogue, Music, SFX or Ambience, then Auto-Match loudness (Dialogue -16 LUFS, Music -23, SFX -20, Ambience -28), clarity EQ, dialogue repair and ducking under tracks with the Dialogue role. Quiet and loud dialogue both measured -16.0 LUFS in the mixdown (editor meter and ffmpeg ebur128). Every preset is built from the existing clip effects, volume and volume automation, and one "Apply all presets" is one undo step.

Limits that remain:

- The SFX preset uses the lookahead Brickwall Limiter and the Ambience preset the Low-Pass Filter (see docs/pro-audio.md). 5.1 surround is supported (sequence layout, surround panner, six-channel AAC in MP4/MOV, 5.1 stems, BS.1770 surround loudness); its limits (stereo clip-level effects, stereo down-mix monitoring, six-channel Opus is not available; AC-3 / E-AC-3 delivery is covered in docs/PREMIERE-GAPS.md) are listed in docs/pro-audio.md.
- Auto-Match is limited by the +12 dB clip gain ceiling; a clip that needs more shows a warning and lands short of the target.
- Ducking is live: it follows the Dialogue clips when they move or trim (docs/pro-audio.md). It reacts to dialogue clip presence, not to speech level inside a clip. Ducks baked by earlier versions stay as keyframes until Duck is switched off and on.
- Matching is not repeated when you change the clarity or ducking options (it would re-measure every drag); press "Match again" if the effect chain changed the level.
- The panel only touches effects it added. If you edit one of them it is kept as yours and not overwritten; Clear Audio Type removes only the panel's own effects and restores the gain and volume lane it replaced, unless you edited those afterwards.

## Interchange (nests and multicam)

- XMEML multiclip layout (`multiclip > angle`, with an extra `offsetseconds`) follows Final Cut Pro 7 from memory and was not opened in Premiere Pro or DaVinci Resolve; unknown hosts still get the active-angle clips. Imported multiclip sources get sync method "manual" (the angle offsets are exact, but no audio-sync confidence exists).
- Importing a multiclip needs at least two angles with media; otherwise the cuts import as ordinary clips with a warning. Angle audio routing (a fixed audio angle) is not carried.
- FCPXML import keeps only the selected angle of an `mc-clip`; OTIO and EDL do not carry multicam at all (flattened to the active angle).
- OTIO writes every instance of a nest in full (OTIO has no shared definition); the importer re-shares them only when the `nestedSequence.id` metadata is present, i.e. for OpenReel-written files. Foreign OTIO stacks import as one nest per stack.
- Nests keep retime (speed, reverse), opacity and level; other clip effects on a nest clip are dropped on export and reported. Speed ramps / freeze frames on a nest clip are exported as the constant speed only.
- OTIO output was validated with the reference `opentimelineio` library (0.18.1) by `packages/core/scripts/validate-otio.py` on a developer machine; CI does not run it. FCPXML nests and multicam are DTD-validated; XMEML has no public schema and is checked by `validateXmeml` and `xmllint` only.

## Interchange (AAF)

- AAF export and import carry the edit only: tracks, clip source ranges, constant speed and reverse, video dissolves, constant clip and track levels, markers, edit rate and start timecode. Effects, colour, titles, transforms, opacity, nested sequences, audio retiming, fades, pan, keyframes and marker colours are not carried (the export report lists them per clip). Media is referenced by path and name and never embedded; imported AAF media is relinked by file name or becomes an offline placeholder, and embedded essence in a foreign AAF is not extracted.
- The files were checked with pyaaf2 (an independent AAF library) and read back by the importer; they were NOT opened in Avid Media Composer, Premiere Pro or DaVinci Resolve. The container, class and property layout follows pyaaf2's, which those hosts read, but host-specific behaviour (linked-media resolution from the ImportDescriptor, transitions at clip boundaries, stereo as two mono slots) is unverified. The pyaaf2 tests are skipped on machines without `pip install pyaaf2`.
- A dissolve borrows frames from both neighbours (AAF semantics). Without enough source handle it is shortened, or written as a cut, and reported.
- The AAF start timecode is written as 01:00:00:00 and is not stored on import (OpenReel sequences have no start timecode).

## Hue curves, Premiere-order colour pipeline, working colour space and HDR export

Shipped and verified in a real browser (`apps/web/e2e/color-pipeline.spec.ts`, `fallback-color-pipeline.spec.ts`, `hdr-export.spec.ts`; unit tests in `hue-curves.test.ts`, `lumetri-pipeline.test.ts`, `color-output.test.ts`).

- **Hue curves.** Hue vs Sat, Hue vs Hue, Hue vs Luma and Luma vs Sat in the Color tab (Hue Curves). A point at 0.5 is neutral; Hue vs Sat and Luma vs Sat scale saturation by 0 to 2, Hue vs Hue rotates up to 90 degrees, Hue vs Luma shifts lightness by up to 0.25. Each curve is baked to a 256-entry float LUT; the WebGL2 shader and the CPU reference read the same LUT and run the same arithmetic. In the e2e card (hue x saturation x lightness, all four curves plus wheels and Basic Correction) the GPU pass and the CPU reference differed by at most 0 levels on the test machine; the spec allows 3.
- **Processing order.** A clip's first grade now uses the Premiere-order pipeline (`pipelineVersion` 2): white balance, then Basic Correction, colour wheels and hue curves in one float pass, then Curves, LUT, HSL and Vignette. Clips that already carry a grade have no version and keep the classic order (wheels, then 8-bit tone/vignette/curves/LUT/HSL, then white balance) exactly as before; the Color tab shows the order and switches it with one undoable click. Hue curves do nothing on a classic clip (the editor says so and offers the switch).
- **ACES colour management (project setting, see docs/colour-management.md).**
  - **Which frames.** ACES mode renders through the float compositor. Frames with an active adjustment layer or text-behind-subject still take the classic display-referred path as a whole (the same rule as the Rec.2020 mode), so the look jumps while one is on screen. Clips that need the 8-bit path (masks, background removal, stabilisation, effects other than blur / sharpen / glow, 3D transforms, emphasis animations, interpolated slow motion, an Input LUT, compound clips, other transitions) are treated as already display-referred: their camera log / wide-gamut input transform is the display-referred one, and the result then goes through the sRGB IDT and the RRT, so they are not scene-referred ACES clips.
  - **Transforms.** ACES 1.3 RRT + ODT only: no ACES 2.0, no Reference Gamut Compression or other LMT, no D60 sim, and the only HDR targets are Rec.2020 PQ 1000 nit (15 nit mid) and the matching HLG; no P3 / Display P3 monitor transform, 2000 / 4000 nit or cinema targets. The sRGB / Rec.709 ODT renders sRGB code 255 (ACES scene 1.0) at display 0.812, which is how ACES behaves; 8-bit titles therefore look slightly grey until HDR graphics white is raised. The camera IDTs are the log decoders already in the product with matrices computed from the published primaries (Bradford adaptation to the ACES white), not the manufacturers' own IDT matrices; they agree with colour-science to 1e-6 but have not been compared with a camera vendor's IDT. HLG is a port without an independent oracle (BT.2100 anchors only); the PQ transform is within a relative 1e-3 of OCIO's builtin, not bit exact.
  - **Grade.** Sliders operate on ACEScct code values (mid grey 0.41, black 0.073), so they do not behave like the display-referred sliders: Basic Correction, wheels and curves are tuned for PQ / display values and are only a first approximation in ACEScct. An sRGB / linear LUT sees ACEScg light with the sRGB curve applied (not a display-referred picture), a "PQ" LUT sees PQ of the working linear.
  - **Preview cost.** The Program monitor renders every ACES frame through the engine (WebGL2 half float; the Float32 CPU reference at about 1 s per 1080p frame where WebGL2 float targets are missing), and the native video-element playback path is off in ACES mode. Playback frame rates in ACES mode were not measured; the float composite of the existing HDR mode costs about 14 ms per 1080p frame on an Apple GPU and the ACES output pass was not timed separately.
  - **Export.** An SDR export in ACES mode is the classic 8-bit encode of the output-transformed frame (tagged like any SDR export, nothing says ACES); HDR10 / HLG exports encode the PQ / HLG transform output. The HDR export path was verified at the encoded-signal level (CPU / GPU parity, unit values), not through a real 10-bit encode, and the desktop (Electron) path was not run.
  - **Scopes** measure the Program monitor, i.e. output-transform code values, not ACEScct. The Working color space setting is ignored while ACES is on.
  - **Input override.** Per footage item (Interpret footage) and per timeline clip (Color tab > Camera input > This clip only, undoable). On the web build the browser still converts tagged HDR / wide-gamut files before OpenReel sees them, so only an override changes how they are read there. The override is available to the user; ACES mode and the clip override are not exposed to the agent / MCP tools.
  - **OCIO** has its own mode with a runtime that evaluates a config's transforms; see the next section. The older Interpret footage > OCIO config import (map a config's spaces onto the built-in presets) is unchanged.
- **Working colour space.** Preview options, Working color space: Rec.709 (default; exports are byte-for-byte what they were) or Rec.2020 (undoable). With Rec.2020 the export converts sRGB-referred pixels to BT.2020 primaries, encodes them as BT.2020 non-constant-luminance YCbCr and tags the file (colr/nclx, verified with ffprobe on an H.264 export: `bt2020` primaries, `bt2020nc` matrix, `bt709` transfer).
- **HDR export.** Export dialog, Custom Settings, Color / HDR: HDR10 (PQ) or HLG, 10-bit H.265 (Main10) in MP4/MOV, BT.2020 primaries, tagged in the container and in the frames handed to the encoder.

Limits that remain:

- **The HDR file path was not encoded end to end in this environment.** The test Chrome has no 10-bit HEVC encoder, so the 10-bit PQ/HLG export is covered by unit tests of the conversion and tagging only, and the e2e verifies the disabled state. The option is enabled only when `VideoEncoder.isConfigSupported` accepts HEVC Main10, and the export fails with a clear message if the browser then refuses the real configuration. A HEVC bitstream's own VUI colour fields are whatever the browser encoder writes; the container tag is set by us.
- **HDR is disabled with the reason shown** on the desktop (ffmpeg) export path, in browsers without a 10-bit HEVC encoder, and for WebM/VP9/AV1/H.264/ProRes. Smart render is bypassed when Rec.2020 or HDR output is on, because stream-copied packets would carry the source's colour.
- **OpenColorIO mode (project setting, see docs/colour-management.md, "OpenColorIO runtime").**
  - **Subset.** The runtime evaluates matrix, exponent, exponent-with-linear, log affine / camera, CDL (clamp and no-clamp), range, ACES Red Mod 1.0, Glow 0.3 / 1.0, Dark-to-Dim 1.0, Gamut Compression 1.3, Rec.2100 Surround, XYZ to xyY / uvY / Luv fixed functions, builtin transforms, groups, file transforms (`.cube` 1D / 3D, `.spi1d`, `.spi3d`, `.csp` with a straight pre-LUT), colour space / look / display-view / view-transform resolution. Not evaluated, and listed per colour space, view and look in the OCIO dialog with the reason: GradingPrimary / GradingRGBCurve / GradingTone / ExposureContrast, AllocationTransform, ACES Red Mod 0.3 (its green / blue handling was not reproduced), RGB to HSV, a matrix that mixes alpha into colour, CDL files (`.cc` / `.ccc`), `.clf` / `.ctf` / `.3dl` / `.itx` / `.mtx` LUTs, a `.csp` with a curved pre-LUT (OCIO resamples it into a 65536 entry table with its own interpolation), nearest and cubic LUT interpolation, the inverse of a 3D LUT (OCIO solves it iteratively), builtins that are tables inside OpenColorIO (ADX, Apple Log, Canon Log 2 / 3), ACES 2.0 output transforms and every ACES 1.x output-transform builtin except SDR-VIDEO_1.0 and HDR-VIDEO-1000nit-15nit-REC2020lim_1.1 (so most of the studio config's views, e.g. SDR Cinema, D60 sim, P3 limited, 2000 / 4000 nit, are listed as unsupported). Named transforms, file rules, viewing rules, `inactive_colorspaces`, includes and `.ocioz` archives are ignored (not evaluated and not needed to run a view). A config LUT that was not provided makes its spaces unsupported until it is added.
  - **Accuracy.** Against OpenColorIO 2.6 (float32, SSE pow / log) on 253 reference conversions, worst relative error (denominator max(|value|, 1)) of the CPU reference: colour spaces 3.3e-5, LUT spaces 2.5e-6, fixed functions 8.5e-6, ACEScc 1.5e-5, looks 3.0e-5, other views 1.6e-5, PQ displays 4.8e-5, HLG display 6.8e-5, the ACES SDR video view 2.1e-4 (BT.1886 amplifies float32 noise near black). The GPU shader is within 9.5e-6 of the CPU reference on every case and within 2.1e-4 of OpenColorIO, measured on an Apple GPU through Chrome / ANGLE Metal in full float (RGBA32F in and out); the half-float compositor adds the usual half-float quantisation on top (engine frames were within 1 code of the CPU prediction). PQ, HLG, ACEScc and the ACES output transforms are analytic replacements for tables / splines inside OCIO, so they are close, not bit exact. The Linux SwiftShader stack was not run for this feature, so the software-GPU tolerance of the e2e (2e-4 GPU vs CPU) is a ceiling, not a measurement; the product flow also passed with WebGPU off and with `--disable-gpu` on this Mac.
  - **Which frames.** Same rule as ACES: OCIO mode renders through the float compositor; frames with an active adjustment layer or text-behind-subject, and clips that need the 8-bit path, take the display-referred path as a whole (those clips enter at the default input space like graphics).
  - **Where colour comes from.** The editor hands OCIO the code values it has: on the web build the browser has already decoded footage to 8-bit sRGB-coded canvas values, so choose an sRGB / Rec.709 input space for ordinary footage (a log or wide-gamut space only makes sense on desktop native decodes that deliver the file's own code values). 8-bit graphics (titles, shapes, subtitles) enter through the project's default input space at graphics white, so a default input space that is not sRGB-like gives graphics that colour. Camera log footage needs its own per-clip colour space.
  - **Grade.** Sliders run on the ACEScct curve applied to working-space values, as in ACES mode, whatever the working space's primaries are; they are a first approximation, not OCIO-aware.
  - **Working space.** Must be scene-referred and convertible both ways. A working space that is not scene-linear is allowed (the dialog says so) and blends in its own encoding.
  - **Export.** An SDR export is the classic 8-bit encode of the view's output, tagged BT.709 like any SDR export whatever the display says. HDR10 / HLG exports write the view's signal into the PQ / HLG tagged stream: choose a PQ / HLG display in the config for them (there is no automatic PQ / HLG view). The desktop (Electron) path and a real 10-bit encode were not run for OCIO.
  - **Cost.** Each distinct input colour space, and the output, is its own shader, compiled the first time it is used (the 253-conversion GPU parity run, a shader compile plus a draw each, took 7 s in total). LUTs are RGBA32F textures read with `texelFetch`, trilinear or tetrahedral in the shader. Per-frame cost in the compositor was not measured separately; without WebGL2 float targets the CPU reference evaluates every pixel through every op: about 0.4 s to decode and composite a 1080p layer and about 2.7 s for the view with a tetrahedral 3D LUT look (one Apple M-series core, Node), so roughly 3 s per frame there.
  - **Storage.** The config text and the LUT files are stored in the project file as text (at most 256 files, 32 MB each, 48 MB in total), so a project with a large 3D LUT is larger, and every undo step of the settings shares those strings. Files named by a config but not provided are listed in the dialog; the folder picker keeps only supported LUT files.
  - **Not exposed to the agent / MCP tools.** The OCIO settings and the per-clip input space are available in the editor only.
- **Source colour management (browser path).** Browsers decode wide-gamut and HDR sources to SDR before the canvas sees them, so on the web build HDR footage still enters as SDR (the float path then grades and encodes it, but there are no highlights above SDR white to keep). The desktop native decode path (ProRes, DNxHD, MXF...) hands over raw code values and, in HDR working mode, 16-bit ones. See docs/colour-management.md, Scene-referred HDR working mode. The preview is not gamut-mapped to the display.
- 8-bit sources (everything the browser decodes, stills, titles) have 8-bit precision inside a 10-bit file; smooth gradients can band. Natively decoded footage on desktop has 16-bit precision.
- "GPU" for grading means the WebGL2 grading engine (there is no WebGPU grading shader in the codebase). The Canvas2D fallback project runs the same WebGL2 pass where WebGL2 exists and the CPU float reference otherwise; a run with no WebGL2 at all was not available to compare.
- Hue curves, the pipeline switch and Rec.2020 are not exposed to the agent/MCP tools. Hue curves are keyframable (see docs/colour-management.md). The Lumetri vignette moves to after HSL on Premiere-order clips (it stays where it was on classic ones).
- Basic Correction in float applies the 256-entry tone curve with linear interpolation (the classic path indexed it by 8-bit level), so a Premiere-order clip differs from the same sliders on a classic clip by at most about one level plus the order change.

## Source colour management and desktop 10-bit HDR export

See docs/colour-management.md for the design. Limits:

- Scene-referred HDR working mode (Rec.2020 working space or an HDR export) composes and grades video / image clips in half float. In float since wave 18: the whole Lumetri grade including the LUT (in its declared space), the HSL bands and the vignette; the blur, sharpen and glow effects; crossfade, dip to black and dip to white transitions. Still on the 8-bit canvas (they enter the float image at graphics white and highlights above SDR white of such a clip are tone-mapped as before): any other effect (vignette effect, HSL Secondary effect, chroma key, pro effects...), masks, background removal, stabilisation, border radius / 3D transforms, emphasis animations, frame-interpolated slow motion, every other transition (wipe, slide, zoom...) and a crossfade / dip where either clip is not float-eligible, compound clips, and text, shapes, stickers, motion graphics and subtitles (graphics, composited at the project's HDR graphics white, 203 nit by default). A frame with active adjustment layers or text-behind-subject renders on the classic 8-bit path as a whole.
- The float effects follow the 8-bit ones in intent, not pixel for pixel: blur is a Gaussian of sigma = radius (capped at a 64-tap half kernel) where the 8-bit shader path is a box blur limited to radius 10; glow is an additive screen above SDR white; sharpen works on the PQ encoding. A float crossfade is an exact linear mix with alpha 1 and honours the clips' transforms, which the 8-bit transition engine does not.
- LUTs carry no colour-space tag in their .cube / .3dl files: the LUT colour space is a per-LUT choice (default Display sRGB) and only HDR projects read it. A LUT authored for Rec.709 gamma 2.4 or a log camera space is approximated by the sRGB choice.
- HDR graphics white is a project-wide value for all 8-bit graphics; there is no per-title override, and the SDR preview (tone-mapped view) of a raised graphics white rolls off like any other highlight.
- In HDR working mode every graded clip uses the Premiere processing order, regardless of its `pipelineVersion`; exposure is a linear gain and the other Basic Correction sliders, wheels, hue curves and Curves act on a PQ encoding of the image, so their feel differs slightly from the same numbers in an SDR project.
- The SDR monitor view and SDR exports of a Rec.2020 project put SDR white at about 97 % (code ~247) to leave headroom for the highlight shoulder. The preview does not use a display's own HDR (canvas `toneMapping: "extended"` / HDR canvas) even where it exists; it always shows the tone-mapped SDR view.
- The web (WebCodecs) build can write HDR10 / HLG when the browser has a 10-bit HEVC encoder (not available in the test Chrome, so that file path has unit and GPU-parity coverage only); its sources arrive SDR, as above.
- A preview render-cache frame is never used for an HDR export (it holds only the tone-mapped 8-bit view); upscaling replaces the frame, so an HDR export with AI upscaling on falls back to the 8-bit conversion.
- Mastering display metadata is fixed (BT.2020 primaries, D65, 1000/0.0001 nit range). MaxCLL / MaxFALL are now measured from the rendered frames of a PQ export and returned in the export stats and shown in the finish notice, but the HEVC stream still declares 1000,400 (libx265 needs the values before the first frame; no second pass or SEI rewrite exists). HLG exports are not measured.
- The resampler is bilinear in linear light; a large downscale of a layer can alias more than Canvas2D's "high" quality smoothing.
- The 16-bit native decode is only used for clips on the float path; its frame cache entries are 8 bytes a pixel (a 4K frame is 66 MB), so the cache holds half as many frames as the 8-bit path.
- Hue-curve keyframes animate each control point's output value (y); the point positions (x) are fixed while a point is animated.
- The Electron e2e `apps/desktop/test/hdr-export-electron.test.ts` (`pnpm --filter @openreel/desktop test:hdr-e2e`, needs a `VITE_OPENREEL_E2E=1 pnpm --filter @openreel/desktop build` and ffmpeg/ffprobe) was run for this change and passed, including the PQ highlight check.

## Camera RAW

DNG stills and CinemaDNG sequences import on web and desktop with RAW Source Settings (white balance, exposure, highlight recovery, demosaic quality, output colour space). Details and the format matrix are in `docs/raw.md`.

Limits that remain:

- **Proprietary RAW is not decoded by OpenReel.** CR2/CR3, NEF, ARW, RAF, ORF, RW2, PEF and the other vendor stills import only on the desktop app for macOS, through Apple ImageIO (`sips`): Apple chooses white balance and tone and the RAW Source Settings controls are unavailable for those items. On the web and on Windows/Linux they are refused with "convert to DNG". No LibRaw/dcraw WASM build is bundled.
- **BRAW, R3D and ARRIRAW are not supported** (proprietary vendor SDKs). Export DNG sequences or ProRes from the vendor tool.
- **The decoder was verified on synthetic DNGs only.** No real camera DNG was available, so camera-specific behaviour (maker profiles, lens opcodes, unusual tag combinations) is untested. The macOS ImageIO path was verified through the real `sips` handler with a plain image, never with a real camera file (ImageIO rejects the synthetic DNGs).
- **DNG features not supported**: lossy and deflate compression, floating-point data, X-Trans / non-2x2 / four-colour sensors, opcode lists (lens correction), noise profiles, profile tone curves and LookTables. These files are refused or developed without those corrections. There is no Adobe-style baseline tone curve: the look is linear plus an sRGB curve, so it is flatter than Lightroom / Camera Raw on the same file.
- **Output is 8-bit.** The developed image is an 8-bit sRGB-encoded bitmap with a highlight shoulder. The scene-linear Float32 result (`developRawLinear`) exists but is not yet fed into the Rec.2020 / HDR working mode, so RAW highlights above the shoulder do not reach HDR exports as true HDR.
- **CinemaDNG sequences are baked, not live.** The frames are developed once at import (as-shot settings, sRGB, up to 3840 px, H.264) and the DNG frames are not kept, so the settings cannot be edited afterwards; re-import to change them. Web needs a browser that can encode H.264 with WebCodecs. Audio files that ship beside the frames are not imported. Frames must be numbered with three or more digits in the same folder pick.
- **Images above 6144 px on the long edge are downscaled** (integer box filter) in preview and export alike.
- **Demosaic is bilinear or Malvar-He-Cutler**, not AHD or an algorithm tuned per sensor; fine detail and false-colour behaviour on very sharp lenses is below the best RAW converters. Noise reduction and sharpening are not applied.
- **Crop mode** on a RAW still shows the 320 px library thumbnail behind the crop handles, not the full-resolution development.
- **Not run:** the Playwright spec `apps/web/e2e/raw-import.spec.ts` was written but never executed (the heavy-run lock could not be acquired), so the browser flow (dialog, one undo step, preview vs export renderer, CinemaDNG bake) is unverified end to end.

## Linked compositions

Live linked compositions (see [linked-compositions.md](linked-compositions.md)) are verified by unit tests (core, web store, desktop relay). Limits that remain:

- A composition is a graphics document. Only text, shape and SVG clips (or an existing graphic) can be replaced with one; video, image and audio clips cannot. Use Nest for those. Motion compositions (`motionCompositions`) are not linkable: this build has no editor for them.
- Only number controls for opacity, rotation and X/Y position can be keyframed. Text, colour, font size, width/height and the combined Position control cannot.
- The composition window edits layers and controls; it has no timeline of its own, and its preview is a still of the hold pose, not playback.
- Edits from a composition window and from the editor at the same time are not merged: the window's edit on an outdated revision is refused and the window shows the current version.
- Render and Replace in the browser renders opaque H.264 (no transparency); only the desktop app renders ProRes 4444 with alpha. A rendered composition is not re-rendered automatically when the master changes; it is marked out of date.
- XML, FCPXML, EDL, OTIO and AAF carry no graphics. A rendered composition exports as its media clip; a live one is dropped with a warning (it is not rendered for you on export).
- The desktop two-window flow is covered by hub/IPC unit tests; a real two-window Electron run and the browser end-to-end spec were not run in the same environment unless noted in the wave report.
- Deleting a rendered clip from the timeline leaves its composition record behind, unused; the live layers cannot be restored from it. Use Restore Unrendered (or undo) instead of deleting the rendered clip.
- Portable edits (`createPortableEdit`) refuse projects with linked compositions, like other graphics.

## Real-time collaboration

See docs/collaboration.md for the design and security model. Limits:

- **Media is not synced.** Peers get placeholders (name, size, modified time) and relink their own files. Importing media on one machine is not an action: the file stays local, and collaborators see the item only when it is used by a shared edit. Media-import actions are reported as "not shared".
- **Conflicts are rejected, not merged.** Concurrent edits to the same clip, the same track (any clip on it), the same media item or the bin tree: the second op in is rejected and rolled back with a notice; project-wide replacements (frame-size change with graphics scaling, `project/applyEditSnapshot`) conflict with everything concurrent. There is no text/property merging inside one clip.
- **Grouped edits are not atomic across the wire.** A multi-step edit (one undo group) is sent as separate ops; if one is rejected the others stay.
- **Offline edits older than the room's retained history (about the last 500 ops) are rejected as stale**, and the local copy is replaced by the shared project. Offline work is not saved as a separate copy.
- **Edits that bypass the action system are local.** Switching the active sequence, creating sequences, and any store-only changes (UI layout, track targeting, playback) do not sync. Playheads and selections are shown as presence only.
- **Locks are soft** (anyone can take over; they expire after two idle minutes) and cover bins and the active sequence only, not tracks or single clips. There is no lock control inside the project panel yet; use the Collaborate dialog.
- **Security.** The server does not validate actions or the conflict keys an author declares; editors are trusted. Room access is a bearer link (anyone holding it joins); there are no per-user accounts, revocation, or audit trail, and a link cannot be revoked short of abandoning the room. Cloud identities are still the dev shim.
- **Text, shape, graphics and other overlay clips** sync through their actions but the title/graphics engines are re-synced from the project only after each remote batch; rapid concurrent overlay edits were covered by unit tests only, not an end-to-end run.
- The Durable Object itself was exercised through a fake `DurableObjectState`/socket harness (the real `RoomCore` and storage layout), not a live `wrangler dev`/miniflare instance, and nothing was deployed.

## Audio Channels

- Waveforms for a mapped clip are recomputed by decoding the whole file; media over 200 MB keeps the unmapped waveform (playback and export still follow the map).
- Edits to a channel map made during playback take effect when playback restarts, like other audio edits.
- Channel maps are verified end to end for WAV and for AAC video sources; exotic codecs that the browser cannot decode natively go through the ffmpeg fallback, which keeps up to six source channels only when a clip is mapped to a channel beyond L/R or to 5.1.
- **Multichannel source patching** (Source monitor A1..An indicators, Modify > Audio Channels on a project item): Insert, Overwrite, drag from the Source monitor, Fit to Fill, Insert / Overwrite from the Project panel, Add to timeline and Project-panel drops all place the picture plus one audio clip per enabled channel group. Add to timeline and drops never overwrite: groups take tracks that are free for the clip's length, new audio tracks otherwise (so they ignore a patched track that is occupied). Replace keeps a sound clip's slot (A1..An) in the new source's layout and clears the old clip's stream and channel map. Files whose audio streams differ in width (mono beside stereo) are grouped per stream, from the widths the importer reads (`metadata.audioStreamChannels`: mediabunny tracks, the desktop ffmpeg probe, the ffmpeg.wasm probe); projects imported before this have no per-stream widths and treat every stream as the file's one channel count until the file is re-imported. A 4-channel single stream is grouped as four monos ("Use file"), so Add to timeline of such a file now places four audio clips rather than one. The patch indicators and their per-channel track patches are editor state, not saved with the project; the layout (`channelLayout`), clip maps and slots are.
- **Smart render and channel maps.** Smart render copies picture only; sound is always the mixdown, so a clip's channel map cannot be lost by a stream copy (checked with a 4-channel source, two channels deleted, smart and full export: both carry exactly the kept tones). The sound clips of a video source on audio tracks are fully transparent and no longer count as picture over the real clip (before, a multichannel edit of a video copied no frames). A clip that is invisible for another reason (opacity 0 without opacity keyframes) is ignored the same way.

## Speaker detection (captions)

Detect speakers runs entirely on this device and uses a small voice-print (MFCC statistics plus pitch) with clustering, not a trained speaker-recognition model. No such model is bundled, and nothing is downloaded or sent off the machine.

- **Accuracy on real voices is limited.** It separates clearly different voices (for example a low and a high voice) well, but similar voices can be merged into one speaker and one voice can be split into two. In a test with three synthetic voices reading different sentences, Auto and a fixed count both got only some of the passages right. Treat the result as a first pass and check the labels.
- **Overlapping speech is not separated.** A caption passage is assigned to a single speaker.
- **Fixing the speaker count helps only when you know it.** Auto picks the count from the clearest gap between voices and can be wrong; the speaker-count menu overrides it.
- **Re-running detection replaces the labels,** including passages you reassigned by hand. Renames, colours and positions of speakers that are still found are kept.
- **Clearing a passage's speaker restores the caption look it had before it was labelled,** which discards style edits made to that caption in between.
- **Clips with no audio track** cannot be labelled; Detect speakers says so.
- **Merging** two speakers is the "Merge into" menu on a speaker row (or renaming one onto the other); it is one undo step, but it cannot split a merged speaker again except by undo or by reassigning passages one by one.
- **No in-picture "Speaker: " prefix.** Speakers are shown in the picture through per-speaker caption colour and position. Names are written into exported captions (SRT prefix, WebVTT voice tags, TTML agents) unless "Include speaker names in the export" is off.
- The only real-voice evidence is a short fixture of two synthetic text-to-speech voices; no recorded human interviews are in the test suite.

## Caption translation

- **Machine translation quality is the engine's.** Translation uses the connected AI model or the browser's on-device Translator API (Chrome 138+, language packs may download). Neither was verified against a live provider in automated tests (mocked clients and a Translator test double); with neither available the Translate tool says so and adds nothing.
- **Translated cues drop word timings**, so karaoke-style word animations fall back to whole-cue display. Cue timing, style and speakers are preserved.
- **A translation is kept out of the picture by default** (its cues are hidden) so two languages never overlap. Choose which track is shown with "Show this track in the picture"; showing one track hides the others. Sidecar and embedded caption files still include every track.
- The browser engine translates one cue per call, so long tracks take a while.
- **No bundled offline translation model.** On-device translation exists only where the browser provides it (Chrome 138+); otherwise the only route is the AI provider you connected, and cue text is sent to that provider only when you press Translate. Nothing is sent otherwise.
- **Long translated cues are re-segmented.** A cue whose translation no longer fits two lines of 42 characters, or runs past 7 s, is split at sentence, clause then word boundaries, sharing the original time span in proportion to text (never shorter than 0.83 s per piece). A cue that reads far too fast (over 15% above 17 characters per second) may borrow following silence, never past the next cue. Slight overshoots keep the exact timing and are left for the caption QC panel to flag; where the time is simply not there, no split can make it readable.
- **Split pieces follow their source speaker** by time overlap, so reassigning a passage re-labels its translated pieces too, but a piece that straddles two source passages takes the speaker of the one containing its midpoint.

## Caption file formats (SCC, MCC, EBU-STL, TTML, transcripts)

Imports list what a file carried that the caption model cannot hold, in the import notification (Project panel and File > Import captions) or the Transcript panel notes, and in `data.issues` of the `import_captions` agent tool. These are the limits behind those notes.

- **CEA-608 positions are approximate.** Row and indent become WebVTT cue settings inside an 80 % title-safe area (row 1 is at 10 % of the height, row 15 at 90 %). Plain bottom-centre captions keep the default caption position. A caption with different indents on its lines takes the left-most indent for all of them, and blank rows between lines are joined. Roll-up captions import as the sequence of windows the viewer saw, positioned by their base row.
- **One colour per cue.** PAC and mid-row colours (and EBU teletext colours) become the cue colour; a cue that changes colour inside takes the first colour for all its text and says so. Flashing, background colours and boxes are ignored and counted. Underline and italics are kept only when "keep style tags" is on (it is off by default and strips `<i>` / `<u>`).
- **One caption channel per import.** CC1 is read unless the CC1 to CC4 picker or `ccChannel` says otherwise. The Text service (T1 to T4) and XDS metadata are never imported; they are counted in the notes. Captions on field 2 (CC3 and CC4) exist only in MCC files; an SCC file is field 1.
- **MCC: CEA-708 is reported, not decoded.** A file whose captions are only 708 services imports as empty with that explanation. Export writes the same CEA-608 CC1 captions as SCC (one CDP per frame, field 2 and 708 slots padded). The `U` alias is read as `E1 00 00 00` (ffmpeg's reading; some files disagree about the number of zero bytes) and never written. MCC V1.0 and V2.0 are read; V2.0 is written. Timecode rates 24, 25, 30, 30DF, 50, 60 and 60DF are read; export is at 24, 25, 29.97 or 30 (the project rate is halved above 30 fps).
- **EBU-STL positions are approximate.** The vertical position is a row number relative to 23 rows (teletext) or the file's maximum row count (open subtitling), mapped to a percentage of the picture height; subtitles that end in the bottom four rows keep the default bottom position. Justification left and right use an 80 % wide box. Character code tables 00 to 04 decode (ISO 6937 and ISO 8859-5 to -8); right-to-left scripts are read in storage order and are not re-ordered. Teletext mosaic graphics are dropped, double-height and double-width are shown at normal size, and extension blocks are read as one subtitle (cumulative sets are accumulated). Subtitle groups other than the first and comment blocks are not distinguished.
- **EBU-STL start time and teletext limits.** Times are imported as written in the file: a broadcast file that starts at 10:00:00:00 lands 10 hours in unless a programme start offset is given (the Transcript panel has one); the import says so. Comment blocks (comment flag set), user-data blocks and mosaic graphics are not imported and are counted in the notes. Teletext colour restarts at white on each row; a subtitle that changes colour takes its first colour for all its text and says so.
- **MCC at 23.976 / 29.97 / 59.94 fps.** MCC has no 23.976 label: `Time Code Rate=24` (also 30 and 60 non-drop) is ambiguous, as in MacCaption and ffmpeg. Export writes the standard label plus an `OpenReel Frame Rate=24000/1001` header line, so OpenReel reads its own files back exactly; other tools ignore the extra line. On import the project frame rate wins when it is one of the two candidates (reported as an import note); then that header; otherwise the label is read as the exact integer rate and a note says so, which drifts about 1 s per 15 minutes on 23.976 footage. 50, 59.94 and 60 fps projects export at full rate (labels 50, 60, 60DF). Invalid dropped drop-frame labels (for example 00:01:00;01) are reported as errors in SCC, MCC and TTML (dropNTSC) and that line or paragraph is skipped.
- **TTML.** `ttp:dropMode="dropNTSC"` is honoured on the SMPTE time base; `dropPAL` and non-NTSC drop modes are not. Vertical writing, ruby and animation are ignored (listed). iTT is read as TTML; no iTT-specific output is written.
- **Timed plain-text transcripts** carry only start times: an end time is the next start, or an estimate from the reading speed (at most 7 s). Untimed text is refused with a message.
- **MCC and transcript parsers load on first use,** so the first import of one of them has a short extra load.
- **Desktop file associations are registered by the installer only.** `.oreel` and the caption extensions are declared in the electron-builder config (see "Ingest presets and file associations"); a development run or an unpacked build does not register them with the operating system, and the Linux and Windows registrations were not run.
- **Not verified against Adobe Premiere.** Interoperability is checked against the specifications and ffmpeg's MCC and CEA-608 implementations; no file written by Premiere, MacCaption or a broadcast encoder was available.

## Ultra Key

- **The Effects-tab card key is a heuristic, labelled "Sample key".** The card previews the effect on your own footage by guessing a key colour from that frame, then narrowing tolerance and transparency until at most about 40% of the frame is keyed. On non-green footage (for example an interview shot) it shows a representative checkerboard-keyed sample, not a prediction of the result. Pick the real key colour with the eyedropper in the Inspector, which samples the Program monitor.
- **Preview/export parity was verified on WebGL2 in headless Chromium** (shader versus the CPU reference used by the Canvas2D fallback and export: 0 pixels off in RGB and alpha on the test frames). It has not been exercised on real WebGPU hardware or in the Electron desktop app.

## Background-task panel

The panel (status bar pill and popover) is a presentation layer over `BackgroundTaskRegistry`; it owns no work. Limits, stated in the panel itself where they affect the user:

- **Pause is per export-queue only.** Pause and Resume exist only for export-queue jobs, and they act on the whole queue (a queued row reads "Export queue is paused" and Resume starts the whole queue). A running export, proxy job, transcription, import, scene detection, beat detection or tracking run cannot be paused; those can be cancelled. The panel footer says so.
- **Import Cancel discards, it does not stop the decode.** The decode keeps running in the background and its result is thrown away. Retry re-runs the full import action; caller-specific follow-ups (for example placing the clip on the timeline) are not replayed.
- **Cleared rows stay cleared for the session**, including mirrored export-queue rows. A retried job shows again. Finished history (40 rows) is not persisted across reloads.
- **Proxy history is session-only.** A proxy that finished or was cancelled shows as such until cleared; proxies that were already ready when the editor loaded are not listed.
- **Not exercised on real footage or hardware:** scene detection, beat detection, transcription, motion tracking, desktop copy-to-project and the desktop native proxy rows, and import cancel on large media. They are covered by typecheck, registry unit tests and synthetic e2e only.
- The popover opens upward over the timeline; it has no pin or dock mode.

## Keyframe temporal interpolation

- **Numeric properties only.** Auto Bezier and Continuous Bezier need a numeric value to compute a tangent; keys on non-numeric properties (colour strings, text) ignore those two types and keep their normal easing.
- **Hold belongs to a whole segment.** Hold is an outgoing type by definition (the value is held until the next key), so choosing Hold with "Both sides" applies it to the outgoing side only. Choosing Linear, Bezier or an Auto type on the In side of the key that follows a held segment converts that segment, because both ends share it. Ease In is always the In side and Ease Out always the Out side; the side menu is ignored for them.
- **Continuous Bezier always links both sides.** Applying it to one side links both. Editing a single handle keeps the link and mirrors the other side's tangent; replacing a whole segment (an ease preset, an easing change) unlinks it.
- **Handle time influence is preserved, not chosen.** Auto and Continuous re-derive the tangent (slope) and keep each handle's existing time length (one third for fresh Auto handles). Influence can be changed by dragging a handle in either graph (an Auto key then becomes Continuous Bezier); there is no numeric field for it.
- **Dragging an Auto handle only links when the key is fully Auto.** A key whose two sides are both Auto becomes Continuous Bezier when either handle is dragged and the other handle follows. If only one side is Auto (the other is a hand-tuned or plain handle) the dragged side becomes a plain Bezier and the other handle is left alone.
- **`ease-in-out` is not converted on load.** `ease-in` and `ease-out` map to exact cubic Beziers (identical values, proven in `keyframe-migration.test.ts`) and are rewritten to Bezier handles when an older project opens. The legacy `ease-in-out` is two joined quadratics and cannot be one cubic, so it keeps its named easing and its exact old curve; its graph handles are the closest Bezier (the 0.42 / 0.58 preset), which is only used if you edit them. Other named easings (bounce, elastic, easeInCubic, ...) are untouched. Text, shape, SVG and sticker overlay keyframes are not migrated either.
- **Agent edits that add or remove keys do not re-derive Auto tangents.** `add_keyframe`, `remove_keyframe` and `set_clip_keyframes` write the keys you give them; Auto and Continuous handles are re-derived by the editor, by `set_keyframe_interpolation` and by `set_keyframe_handles`. Run `set_keyframe_interpolation` again after bulk key edits.

## Keyframe graph and spatial paths

- **A spatial path needs matching X and Y keys.** Position is two scalar properties. The route exists only when every `position.x` key has a `position.y` key at the same time (and the other way round); otherwise the axes interpolate independently exactly as before, and the Spatial menu is not offered. Moving only one axis's key in time breaks the pairing until the other follows.
- **Timing along the path comes from the X key.** Speed along the route follows the temporal interpolation (easing and handles) of the `position.x` key of each segment; the Y key's temporal settings are ignored while a spatial path is active. Apply temporal types to both axes together to keep them in step.
- **Overshoot continues along the end tangent.** A temporal curve that overshoots 0..1 (bounce, elastic, handles above 1) continues in a straight line past the segment's end along its end tangent instead of following a curve.
- **Main-timeline clips only.** Position handles on the Program monitor, the Spatial menu and the speed graph's handle editing act on clips on the main timeline (the keyframe editor's scope). Text, shape, SVG and sticker overlays (which use normalised position) and motion-graphics layers keep linear position interpolation.
- **Speed graph.** Each property curve is scaled to its own peak. Hold segments and non-numeric properties have no speed handles, and the speed graph does not draw a combined 2D position speed, only the speed of each axis. The graph drags a whole selection only in the value graph.
- **Cross-clip paste of effect keys.** Effect keys follow onto the target clip's only effect of the same type; when the target has none or several, those keys are skipped (the agent tool reports how many).
- **Not exercised:** the Electron desktop app and real WebGPU hardware. The web e2e ran on desktop Chrome with this Mac's GPU flags; preview and export agreed with the evaluator to under one pixel at 640x360.

## Encoder choice and proxy presets

- **The browser capability probe asks WebCodecs about one representative profile per codec** (H.264 High L4.0, HEVC Main, AV1 Main, 5 Mbps) at the export size and frame rate. A machine can accept that and still refuse the project's exact bitrate or profile; the export then fails with the encoder's own message (Hardware and Software are strict, they never switch kind silently). Auto is the only choice that falls back.
- **Hardware encoding on the desktop is not offered with Two-pass VBR or Rec.2020 / HDR output** (hardware encoders have no two-pass mode; HDR needs libx265 for the HDR metadata). Choosing Hardware there is refused with the reason; Software and Auto work. A failed hardware encode with Hardware chosen is reported, not retried on the software encoder.
- **Hardware encoders (VideoToolbox, NVENC, Quick Sync, AMF) were exercised end to end only on VideoToolbox (macOS).** NVENC, Quick Sync and AMF are covered by argument and capability-mapping tests, not by a run on that hardware.
- **Create Proxies with a preset only targets clips that have no proxy (or a failed or missing one).** To rebuild an existing proxy in another preset, use Rebuild on the row after changing the preset in the Proxies panel.

## Ingest presets and file associations

- **Desktop only, and the presets live in this install's browser storage** (app settings), not in the project and not synced between machines. A project keeps a copy of the profile it uses, so another machine builds proxies the same way, but it does not get your preset list. A preset's custom destination folder is a path on this machine.
- **Frame rate is always kept.** There is no frame-rate conversion in a proxy preset. DNxHR is written as DNxHR LB or SQ in a .mov; DNxHD (fixed bitrate) and HQ, HQX, 444 are not offered. ProRes 4444 and XQ are not offered.
- **Burn-in needs a drawtext build and a font.** The bundled ffmpeg sidecar has drawtext (verified on the macOS arm64 sidecar). A different ffmpeg without it, or a machine with none of the fonts the app looks for (Menlo / Monaco on macOS, Consolas / Courier on Windows, DejaVu Sans Mono / Liberation Mono on Linux), fails the job with a message instead of writing a proxy without the text. Windows and Linux were not run. The timecode burn-in starts at the file's start timecode when ffmpeg can read one, else at 00:00:00:00; it counts at the file's frame rate (drop-frame labels are passed through for a start timecode written with a semicolon; that was checked on one 29.97 file). Burn-in text is drawn at a fixed size relative to the frame height and is not themable.
- **xxHash64 is a JavaScript implementation** (about 250 MB/s on one core here, against about 700 MB/s for Node's MD5), so MD5 is the faster verification; SHA-256 is the default. All three read the copy back from disk once after writing, so a verified copy costs two reads of the file plus the write. xxHash64 is for matching a ledger from another tool, not for security.
- **Copy verification reads the copy back through the operating system's cache,** so a fault that only shows after a cache flush may not be seen. A copy is never made over an existing file; an identical copy found by name after an interrupted run is kept, a different one with the same name gets a number.
- **Background copies have no operating-system priority change.** Proxy encodes run at nice 10 (below normal on Windows); a copy is one Node stream in the main process, one at a time, which keeps it off the UI thread but does not lower its disk priority.
- **A copy needs a saved project** (its Media folder sits beside the project file); with an unsaved project the copy is refused with a message and "Copy and create proxies" does not start. Copy jobs restart from the beginning after a restart; there is no byte-range resume.
- **Copy and create proxies makes proxies for video only.** Audio and still images are copied without a proxy. If the copy of a clip fails, its proxy is not built.
- **Attach by pattern reads one `{name}` template** against the clip's file stem, case-insensitively; it does not support wildcards, regular expressions, or timecode / reel matching. Matching uses duration (within 1 % or 0.25 s) and frame rate (within 0.05 fps). A search stops at 8 folder levels and 200,000 files and says so. Same-named proxies in several folders that all fit are reported as ambiguous and none is attached.
- **File associations were not registered on a real machine.** The electron-builder configuration and the argument and `open-file` routing are covered by tests (`file-associations.test.ts`, `open-files.test.ts`, and a real Electron run of a first launch and a second launch with files on the command line); the Info.plist of an unsigned macOS `--dir` pack was read back (eight document types, ranks as above, and the exported `video.openreel.project` type), but no build was installed, and the Windows registry entries and the Linux MIME database were not inspected at all. Nothing was signed or notarised. Caption files are registered at the "alternate" rank on macOS, so double-clicking a `.srt` may still open another app until the user picks "Open With OpenReel". `.json` project files are not associated.
- **Opening files with no project open asks in an in-app dialog** which project to import captions into (Choose project opens the system project picker; Cancel or Escape imports nothing). Several caption files open together import into the same project one after another (each its own undo step); several project files open only the first.

- Import only, and read from hand-authored fixtures: a project saved by Adobe Premiere Pro has not been tested. Treat the import report as the source of truth for what arrived.

## Premiere Motion Graphics Templates (.mogrt)

- Import only (there is no `.mogrt` export), and Premiere-authored templates only. After Effects-authored ones (`.aegraphic`) are detected and refused with a report; their compositions cannot be rendered here.
- **Read from hand-authored fixtures: a .mogrt written by Adobe has not been tested.** The graphic XML layout is a reconstruction (Adobe does not document it); an unfamiliar file may be refused ("no readable graphic") or import with layers skipped. Media-replacement controls, scale / position sliders and unbound controls are not; text stroke colour is not editable. A slider's range comes from the file.

## Dolby Digital (AC-3) and Digital Plus (E-AC-3)

- AC-3 / E-AC-3 inside MP4, MOV and MKV is desktop only (the native ffmpeg sidecar). The browser writes raw `.ac3` / `.ec3` audio-only files through ffmpeg.wasm and refuses AC-3 video-file tracks with a desktop-only message.
- Stereo and 5.1 only. Dialnorm is the only Dolby metadata written; no DRC profiles, no Dolby Atmos (E-AC-3 JOC) and no 7.1.
- The sample rate is 44.1 or 48 kHz (anything else is written at 48 kHz).
- The browser path is tested at the unit level and by confirming the bundled core lists the encoders and muxers; the ffprobe and per-channel level checks run against the desktop sidecar only.

## Spectral editing

- **Selections:** box, frequency band (always the whole source), lasso and brush. Magic wand and harmonic selection are described below. A lasso edge is straight on the time / log-frequency plane the editor draws on; a brush is an ellipse of fixed seconds x octaves, so at low frequencies it is narrower in Hz than the STFT's main lobe (about 47 Hz at 48 kHz) and leaks, so paint wider there.
- **Source-time regions.** Regions live in the clip's source time, so trimming the clip does not move them; a region outside the clip's in/out range stays stored but is inaudible. Behaviour under speed changes was not tested.
- **Old projects keep working, new ones need this build.** A project that only has box regions with attenuate / remove is saved exactly as before (no version marker). Once a lasso, brush or heal region exists the effect is saved as `version: 2`, and once a magic-wand region, a harmonic region or a single-channel edit exists as `version: 3` (a list that uses none of those is still written as 1 or 2, so rectangle-only projects stay bit-identical, with the same cache key); an older build ignores regions it does not understand, so opening such a project in an older build plays the clip without them.
- **Remove is interpolation, not resynthesis.** It fills the region from the bins above and below (and the frames around it) with a noise-like phase; it clears steady tones, hum and short clicks cleanly, but broadband or fast-moving sounds inside the box leave audible artefacts.
- **What Remove and Heal are each for.** *Remove* is a smooth interpolation of the surrounding magnitudes with a noise phase: cheap, and the lowest error against what lay underneath whenever that is silence or cannot be predicted, but its fill is 5 to 14 dB quieter than the background around it, so over a noise floor or music it leaves a notch. *Heal* refills the selection with a model of the background: the expected power is averaged over several untouched cells on every side and interpolated in power (not magnitude), the phase of each bin is continued from the left of the gap and backwards from the right (phase-vocoder propagation measured over three frame pairs and three bins), and a fixed 6 consistency passes make the fill a real signal while a tile-averaged gain brings it back to the target power. Bins that behave as a stable partial at both ends of a short gap, and whose forward and backward predictions agree, continue as that partial; the rest get matched noise. Heal has no hard decision on a noisy value and no data-dependent iteration count. Use Heal when the background stays audible (a noise floor, hum, a held note under a cough); use Remove when you want the least energy left in the selection. There is no automatic per-case default in the editor: the buttons say what each does; the agent's default is heal (`add_spectral_region`, `remove_spectral_tones`, `remove_spectral_clicks`).
- **Heal is numerically stable now; it was not.** The first heal ran 24 Fast Griffin-Lim iterations (momentum 0.99) with a per-cell phase normalisation. That map amplified a 3e-8 input perturbation by 8 to 29 dB (58 dB on the verifier's case), because a near-zero cell makes the normalised phase swing wildly and the momentum feeds it back; the preview and the export decode separately, so that became a -66 dB mismatch. The replacement amplifies the same perturbation by -0.1 to 1.6 dB (remove: about 0 dB), asserted below 6 dB over remove for every case in `spectral-heal-quality.test.ts`; two decodes that differ by one 16-bit LSB give healed outputs that match to better than -55 dB. The browser e2e residual between preview and export for a brush and lasso heal is now -93.7 dB (`spectral-masks.spec.ts`; it was -66 dB), the same order as the linear rectangle edit (-92.9 dB).
- **Measured, remove vs old heal vs new heal** (`spectral-heal-quality.test.ts`; 1.6 s synthetic signals at 48 kHz, 3e-8 perturbation; "err" is the complex STFT error against the CLEAN signal inside the mask, dB re the clean energy there: 0 dB is a hole, +3 dB an equal-level fill uncorrelated with the original, lower is better; "level" is the fill's power against the clean's; "amp" is the amplification):

  | case | remove err / level / amp | old heal err / level / amp | new heal err / level / amp |
  | --- | --- | --- | --- |
  | tone 1 kHz over white noise | 0.8 / -6.1 / 0.1 | 2.9 / 0.3 / 7.9 | 3.5 / 1.0 / 0.6 |
  | tone 1 kHz over pink noise | 0.8 / -6.4 / 0.1 | 2.6 / -1.0 / 14.9 | 2.7 / -0.5 / 0.8 |

  Read it honestly. New heal beats remove on error only where steady partials continue across the gap: a cough over a chord (-2.8 and -5.1 dB against +0.7), and a pure tone or two well-separated tones removed from a gap and healed come back at -10 dB error and 0.95 correlation (ad-hoc check, not asserted). On noise (white and pink, whatever removed it) and on partials that glide, vibrate or beat inside one bin (the vibrato speech, the 2 to 9 kHz chord band where upper harmonics of four notes sit within 20 Hz of each other) nothing can predict the lost samples, so the best a fill can do on raw error is a quiet one: remove scores 0.0 to 1.0 dB by being 5 to 14 dB too quiet, and a fill at the right level scores about +3 dB. Heal chooses the right level: its level is within about 2 dB of the clean in noise (remove: 6 dB low), its texture matches (the log-magnitude spread is within 1.1 dB of the clean's, and 5 to 10 % of its cells are more than 12 dB below the mean, which is what Rayleigh noise itself has, against 29 to 41 % for remove's smoothed holes; the old heal's fill was flatter, spread 1.5 to 2.5 dB too narrow). Where it cannot continue a partial it is no better than remove on error, and on the two chord clicks, one of them with vibrato (-0.29 correlation), it is worse by 0.9 and 4 dB because it commits to a partial it cannot hold. Heal also leaves a little more of the interferer than remove in the mask (the fill is not quieter): 1 to 2.5 dB on the tones and bursts. Against a staircase of rectangle removes along a whistle, the lasso or brush heal still leaves 20 to 40 dB less damage to the surrounding audio (`spectral-heal.test.ts`), and over a plain remove of the same mask it fits the magnitude 0.8 dB better and the surroundings are within 1 dB. For a 3-sample click in speech a 50 ms box above 2.5 kHz brings the local SNR from 1.4 dB to about 10 dB with heal and 11 dB with remove: comparable, and the DeClick effect is the lighter tool.
- **Heal limits.** It continues a partial only across gaps up to about 0.26 s (fading out to nothing at 0.52 s, so a long selection over a tone or hum removes it rather than continuing it) and only if the partial holds one bin and both predictions agree; the phase prediction is good over about 0.1 to 0.25 s of steady partial; there is no gliding-partial or vibrato tracking (the earlier ridge-morph, which was an argmax over shifts, was removed with the rest of the unstable machinery), no recovery of the original phase of a masked harmonic, and no per-channel stereo relation. The fixtures are synthetic; recorded speech and music were not measured. Heal continues whatever steady partial is on both sides of the gap, wanted or not: heal a 0.2 s slice out of the middle of a longer steady interferer (a whistle or hum that carries on before and after the selection) and the interferer is carried through the slice (measured in the verification: 440 Hz tone over pink noise, 0.26 s slice, only about 4 dB of it removed against 16 dB for Remove). Select the interferer's whole length, or use Remove, to take it out.
- **Heal keeps a partial that continues on both sides of a slice.** Heal carries a steady partial across a gap, so healing only a slice of a persistent whistle or hum leaves it audible. The agent tools therefore default to Remove for tones and for partial-duration selections (add_spectral_region, remove_spectral_tones; Heal by default only for a band, a whole-source selection, a tone that lasts the whole clip, or clicks), and say so in data.warning(s) when an explicit Heal would keep a tone. The editor shows a warning with a Use Remove button when a narrow band has steady energy on both sides of the selection. The check looks at up to 0.5 s each side and and needs the partial to hold one pitch (within one 4096-point bin, about 12 Hz at 48 kHz) for at least 60 % of the frames, so a gliding or very short partial can still slip through.
- **Heal is a stereo-unaware fill.** Each channel is healed on its own, so the phase relation between channels inside a healed region is not preserved. A region can now be limited to the left or the right channel (`channel`), but the heal, the wand and the harmonic tracker still analyse the mono mix of the source, so a sound that exists in one channel only is selected from its half-amplitude trace in the mix, and the per-channel edit does not preserve the phase relation between the two channels either. A mono source is its "left": a right-only region does nothing to it.
- **Cost.** A heal runs 6 consistency passes (one inverse and one forward FFT per masked frame each) plus a few box filters over the mask's cells, and measures the phase over 5 frames of context on each side of the mask; a 26 s mask from 0.5 to 8 kHz takes about 4.7 s (a remove: 0.3 s) in the same single thread, the old heal's 24 passes were slower. The first repair of a clip renders before it can play and the cost grows with clip length (not benchmarked on long clips); very long sources (over 400 MB of media) are refused by the editor, and the agent's tone / click finders refuse media longer than 10 minutes.
- **Preview and export play the same repaired samples** (one shared cached repair job, applied before every other clip effect). For the same decoded buffer they are identical (core unit tests compare the samples exactly, lasso / brush / heal included). In the browser the two paths decode the file separately; heal is now a smooth function of its input (see above), so that difference no longer grows: the residual follows the decoding difference like remove does (-93.7 dB measured for heal).
- **Agent tools.** `find_spectral_tones` finds only stationary tones (a gliding harmonic is rejected by design) and needs at least 0.25 s of steadiness; `remove_spectral_clicks` uses a second-difference outlier detector, not the DeClick detector, and heals only above 2.5 kHz. Both need the live editor's decoder (headless hosts return UNSUPPORTED_HOST); add, update, list and remove work headless.
- **Magic wand (measured, `spectral-wand-harmonic.test.ts`).** The wand analyses the clip's mono mix on the edit STFT (2048 / 512), up to 20 s each side of the click, and floods an 8-connected region of cells whose level on 3 x 3 smoothed power is within `toleranceDb` of the clicked cell's (level mode), or whose prominence over a +-10 bin x +-8 frame neighbourhood is within the tolerance of the seed's, one-sided (contrast mode). The selected cells themselves are stored (run-length coded on the STFT grid, with the seed and settings kept for display), so a region renders identically after a reload and never depends on the algorithm again; changing the algorithm only changes what a new click selects. On analytic signals: a click in a 20-click train at 6 dB selects 9 frames over the whole band (0.096 s, so the neighbouring clicks 0.13 s away are untouched, under 0.1 % of their energy in the mask) and holding more than 85 % of the click's energy; removing it lowers the +-20 ms around it by 16.7 dB (the selection stops where a click's tail drops more than 6 dB, so a little of it remains). A 60 Hz hum under white noise is selected as one 4-bin band for the whole 3 s with 99.6 % of its energy and 0.37 % of the noise in the mask, and an attenuation of -60 dB takes it down 26.5 dB (level mode; 26.1 dB in contrast mode, which also picks the 120 Hz partial of the same ridge here). Limits: the tolerance is a threshold, not a model. Raised to 20 dB the same click selection floods through the noise floor and covers the whole clip (3 s); a wide selection of noise-like content is fragmented (the stored mask is capped at 120 000 runs and 4 M cells, and a click that exceeds that is refused with a message rather than truncated); a tone that wanders by more than the tolerance between frames is split in level mode (use contrast mode or a larger tolerance); the seed snaps to the loudest of its 3 x 3 cells, so a click between two close tones takes one. Wand and harmonic regions default to a hard edge (feather 0): a feather thins a band only a few bins wide (a hum wand's removal depth fell from 23 to 17 dB with feather 1). The cells are fixed once created: moving a wand region is not supported (re-click instead), and re-running it with another tolerance needs the source (the editor re-runs the pending selection when you move the slider; an already stored region is re-run through `update_spectral_region` with the live decoder).
- **The wand leaks a transient that sits on a steady chord (independent verifier, not fixed).** A click on a cough laid over a sustained chord, at the default 6 dB tolerance, selects the cough and also floods into the chord's partials: 21.7 % of the selected energy is chord, so removing it takes a notch out of the music. Local-contrast mode does not help in that case (it does not separate the cough from the partials it overlaps either). The wand is a level-similarity flood fill, not a source separator: wherever a transient and a steady sound overlap in time and frequency at similar levels it cannot tell them apart. Lower the tolerance, use a lasso or brush around the cough, or select with a box and Heal, which does continue the chord.
- **Harmonic selection (measured).** The tracker follows a fundamental with a 2048-point STFT at a 256-sample hop, voting the first 12 partials on a 1-cent grid around a slope-extended prediction (60 cents either side per 5 ms) with a parabolic refinement. On analytic harmonic tones (8 partials, white noise 20 dB below, 48 kHz) the f0 error is: a 5.5 Hz vibrato of +-50 cents on 220 Hz, median 1.4 cents, 95th percentile 6.1, worst 33.9 (worst cases are the first and last frames at the source edge); a glide of 0.8 octave per second, median 1.4, p95 8.5, worst 21.0; a glide with a 6 Hz +-35 cent vibrato on top, median 1.6, p95 11.2. In the browser e2e (4 partials, 5 Hz +-30 cent vibrato over a glide, real click) the median is 4.8 cents and the worst 20 cents. The track starts and ends within 2 ms of a bounded tone (0.800 to 2.101 s for a tone from 0.8 to 2.1 s), and within 0.12 s of it in the browser spec. The track is simplified to at most 512 points (Douglas-Peucker, 0.75 cents or more) and stored; the bands are derived from it, so the region does not depend on the tracker later. Harmonic energy captured against non-harmonic energy included: for the vibrato voice, 97.7 % of the harmonic energy and 2.6 % of the white noise are inside the region, against 97.6 % and 7.8 % for one rectangle 200 Hz to 2.08 kHz over the same time. Removal depth under speech-like noise (`speechLike` with a 5-partial whistle gliding 400 to 700 Hz, -60 dB attenuation, linear so the whistle left is the operation on the whistle alone): the harmonic region takes the whistle down 20.6 dB and keeps the speech at 11.6 dB SNR against the damage; a band over the whistle's fundamental only takes it down 5.0 dB (the overtones remain) at 5.5 dB speech SNR; one band over all five partials takes it down 34.8 dB but leaves the speech at 2.0 dB. So it gets within 14 dB of the brute-force band's depth with 9.6 dB less damage to the speech, and 15.6 dB deeper than the cheap band. The band is never narrower than 1.5 STFT bins (about 35 Hz at 48 kHz) so a thin partial is not lost between sample points; below about 100 Hz of f0 neighbouring partials are then 4 bins apart and the region covers most of the spectrum between them.
- **Harmonic limits.** The seed must be the fundamental: clicking an overtone tracks that overtone as if it were the fundamental (its own overtones are then selected above it). The tracker stops when the partials fade 30 dB under the seed's, stand less than 1.5 times above the between-partial floor, or stop matching the seed's partial-magnitude profile (cosine 0.8) for 4 frames in a row, and carries a brief dropout on its prediction. On a dense mix of several harmonic sources it can follow the neighbouring voice that is louder at the seed's partials; check the readout (the track's start / end and the fundamental's range) before applying. Tracking is limited to 60 s each side of the seed and sources up to 10 minutes. The track holds one pitch per instant: a chord, a polyphonic or inharmonic source (bells, piano low strings) is not followed, and the first and last frames of the source are the least accurate. Remove and Heal fill by the surrounding background, so a Heal of a harmonic region carries a steady partial through a short gap, which is rarely wanted; Remove is the default of the agent tools.
- **Agent tools for the new selections.** `add_spectral_magic_wand` and `add_spectral_harmonic_region` need the live editor's decoder (headless hosts return UNSUPPORTED_HOST), analyse the mono mix of the whole media (not the trimmed part), and are `expensive` like the other analysis tools. `add_spectral_region` and `update_spectral_region` take `channel`; `update_spectral_region` takes `harmonics`, `maxHz`, `bandCents` for a harmonic region and `toleranceDb` / `localContrast` for a wand (the latter needs the decoder too). The tool list snapshot was regenerated for these (2 new tools; the list, add and update descriptions changed).
- **The desktop app was not given its own spectral e2e**; the feature runs from the shared web bundle and was exercised end to end in the web e2e only.

## Watch folders (desktop)

- **Desktop only.** The web app has no folder access, so there is no web equivalent.
- **Polling, not OS events.** Folders are rescanned every 5 s and candidate files are re-checked every 0.7 s; a file must keep the same size and modified time for 2.5 s before it is touched. A copy that stalls for longer than that (a slow network or card reader) can be picked up while still incomplete. Network shares are scanned the same way and were not tested.
- **Ingest needs an open project and an editor window.** With none, files wait (shown as waiting in the panel) and import once a project is open. Imports go through the editor one file at a time, and the import tool's limits apply (files over 1 GiB are skipped and shown as failed).
- **Existing files are not processed** when a folder is added (they are recorded and skipped) and there is no switch for it in the UI (only the saved `processExisting` setting in `watch-folders.json` turns it on).
- **Media export is a re-encode by the bundled ffmpeg**, not the editor's renderer: it applies the preset's size, frame rate and bitrate to the source file (letterboxed to fit) and is not a render of a timeline. Colour management, HDR, LUTs and effects are not applied. Audio-only (WAV) cannot render a project.
- **Project export uses the editor window.** Dropping a project file opens it in the editor (the open project is saved first and is replaced in the editor) and renders it through the export queue, so it is not a background render and it interrupts whatever is open. The project's footage must be reachable: the editor reconnects remembered paths, then searches the folders the project recorded and the folder the project file sits in; media that cannot be found fails the item with the editor's "Relink the original media" message. Only the video presets apply to projects.
- **Duplicates** are detected by content (size plus a hash of the first and last 256 KiB), not by name, so a renamed copy is caught but a file that differs only in its middle is not. The ledger keeps 5,000 entries per folder, so a very old duplicate may be processed again.
- **Verified** with synthetic clips on macOS (arm64) only. Not exercised: Windows and Linux, network drives, long camera-card ingests, 4K render timing.

## Planar and corner-pin tracking

A planar track follows one flat, textured surface. What it does and does not do:

- **Needs texture.** Features are Shi-Tomasi corners inside the quad. A flat colour, a blank wall or a screen showing a uniform fill is rejected ("too little detail"); low-contrast or strongly motion-blurred surfaces track with low confidence.
- **One plane, rigid.** The model is a single homography. A curved, folding or non-planar surface (a flag, a face) will fit a compromise or be lost. Lens distortion is not corrected before tracking; a wide-angle lens bends a large plane away from a homography near the frame edge.
- **Occlusion and loss.** Moving occluders that cover part of the surface are rejected by RANSAC (tested with a box hiding about a sixth of it). If fewer than 8 points survive, or the quad would collapse or flip, the corners are held at their last good position and the frame is marked low confidence; tracking resumes when the surface returns (tested), but a long full occlusion plus a large movement can lose it for good and needs a hand-set frame and "Re-track from here". The re-anchor is to the frame you tracked from, so a surface that turns far away from that view tracks worse (strong foreshortening was not measured); re-track from a later frame in that case.
- **Accuracy is measured on synthetic footage.** Under 1 px at every corner over 64 frames of perspective motion with noise and an occluder (worst 0.41 px). It has not been measured on real camera footage with rolling shutter, compression noise or motion blur, so expect a few pixels there and use "Set corners at this frame" to correct. An independent check with a pinhole-camera plane turning up to 55 degrees out of plane, brightness drift, noise and an occluder over 90 frames gave worst corner error 1.4 px forward and 2.3 px backward (mean 0.35 and 0.78 px), so the sub-pixel figures above do not hold under strong foreshortening.
- **Applied as Transform is a similarity fit.** Position, Scale and Rotation put the clip's frame on the surface's centre, size and in-plane angle. It cannot show perspective or keystone; use Corner Pin for that. Scale X and Y are fitted separately, so a clip with a different aspect than the surface is stretched to match it.
- **Corner Pin maps the clip's own frame**, in percent of the canvas, before the clip's Transform and masks. A full-frame graphic fits best. The effect clamps coordinates to -100 to 200 percent, so a surface far outside the frame is clipped. The monitor handles show the effect's own coordinates, so with a non-identity clip Transform they do not sit on the transformed picture.
- **The mask is four straight edges** with the same point order every frame, interpolated linearly between samples. It follows the surface until the clip's last keyframe and then holds. One planar application per target clip: applying a different mode replaces the previous one.
- **Smoothing** averages corner positions over up to +-10 samples; it can soften a fast move and is off by default.
- **GPU parity was checked on one machine.** The GPU/CPU comparison ran in headless Chrome on a Mac (ANGLE/Metal); other GPUs and drivers, and the software GL stack used on Linux CI, were not run. The corner-pin shader is the same code path the preview and export use.

## Render cache (Render In to Out, persistent)

- **Codec is not ProRes/DNxHR.** Render files are one independently decodable frame per file: all-intra H.264 from WebCodecs (hardware encoder where there is one, `avc1.640034`, constant bitrate), falling back to VP9/VP8 and then JPEG. They are lossy previews (about 50 dB PSNR against a fresh render in the earlier measurement); the ffmpeg sidecar is not used for them. On the desktop the main process only stores the blobs on the scratch disk. A ProRes/DNxHR segment-file pipeline would give higher quality and smaller overhead per file and has not been built. The H.264 encoder underuses its bitrate on smooth content (a 1080p glow/blur frame is about 12 to 30 KB), so the cache is small but the quality headroom is whatever the platform encoder gives.
- **Frame-granular files.** A 10 s 1080p30 range is 300 files; large sequences create many small files. Invalidation is exact to the frame because of this.
- **Restart safety rests on content hashes.** Each cached frame stores the hash of its segment (global sequence settings plus every clip, effect and keyframe, transition, adjustment layer, text and graphic, mask and media identity active at that frame) and is dropped on load if the hash differs, the file is missing or its size differs, the codec or frame size changed, or the project key differs. Compositor changes that alter pixels for an unchanged project are only caught if `RENDER_PIXEL_VERSION` (`packages/core/src/render-cache/segment-hash.ts`) is bumped.
- **Media identity.** Desktop: size and mtime of the source file (`stat`, refreshed when a render starts and at restore) plus the native path. A file overwritten in place with the same size and mtime is not detected. Browser: blob size, type and `lastModified`. Hashes also ignore thumbnails, filmstrips and audio-only edits. Media that is offline when a project reopens delays the restore for up to 20 s; if it never comes back, the render files are left untouched and unused until it does.
- **Sequence bookkeeping is not a pixel input.** The project's `sequences`, `activeSequenceId` and `openSequenceIds` (which appear when a project is saved and reloaded) no longer invalidate the cache; a non-active sequence reaches pixels through the nest projection already fingerprinted per clip. If a future change makes a sequence field pixel-relevant outside `compoundClips`, it must be added to the model.
- **Scratch disk.** One folder named "OpenReel Render Cache" under the chosen location; changing the folder starts a fresh cache there and leaves the old files in place (use Delete all render files first, or remove the folder). The size cap is total across projects: when exceeded, the least recently touched project folders are deleted whole (never the open one) at most every 20 s; inside the open project frames are evicted LRU to the cap. Projects untouched for 30 days are swept when a project opens. A full disk fails the render with a clear message and keeps the frames written so far. Not tested: network volumes, Windows and Linux paths.
- **Web.** Files live in OPFS (IndexedDB when the browser has no OPFS writable streams, memory when another tab already owns the project's lock; other projects' OPFS folders are swept after 14 days); the browser may evict them under storage pressure, which restore treats as missing files. A real page reload cannot reopen the same project without a saved project file, so persistence in the browser is verified by re-initialising the cache layer in the same page (Playwright), not by a reload. Default preview size in the browser is capped at 1920 wide; full resolution is a setting and uses much more quota.
- **Frame size.** "Full resolution" means the sequence size (no 1920 cap). Changing the setting discards the current files. A 4K sequence rendered at full resolution was not measured end to end.
- **Export reuse** ("Use previews") needs frames at exactly the export size and frame rate (so full-resolution previews are what make it apply to 4K exports), is never used for HDR or upscaled exports and is not bit-exact (see export-queue.md). It is the only reuse; the native ffmpeg smart render still stream-copies untouched source GOPs and does not read render files.
- **Not built:** a separate "rendered but stale" colour, rendering during idle time, per-track render selection, and render-file reuse across different projects with identical content.
- **Measured, not guaranteed.** The numbers in `apps/desktop/PERF.md` ("Render cache") were taken on one Apple Silicon Mac while other jobs kept its load average around 10 to 17 on 12 cores, with a deliberately heavy 1080p stack; live compositing there ran at 1.6 fps, which says more about that stack under that load than about a typical machine.

## Enhance Speech

- **It is a denoiser first.** DeepFilterNet3 removes steady and non-stationary noise very well (SI-SDR +8 to +14 dB on read speech with pink noise at 0 to 10 dB SNR) but reduces room reverb only modestly: on speech convolved with a synthetic room (RT60 0.45 s) plus noise at 10 dB SNR the gain was +2.1 to +4.0 dB SI-SDR against the dry voice, and reverb alone (no noise) moved it by 1 dB or less. Premiere's Enhance Speech does more dereverberation; use Reduce Reverb (below), which runs before it, for a roomy recording.
- **Speech only.** Music, singing and sound effects in the same clip are treated as noise and can be damaged; use Mix to blend the original back in, or keep music on its own track. It was tuned on and tested with English read speech and synthetic noise and rooms, not with a spread of real field recordings, accents, languages or very low-level voices.
- **Competing talkers are not removed and can make things worse.** Background speech (a second voice, a TV, crowd babble) is not treated as noise. In an independent check with synthesised speech and a second synthesised voice as the "noise", SI-SDR against the clean voice fell by 2.8 dB at 5 dB input SNR and 3.6 dB at 10 dB, because the network kept the interferer while attenuating parts of the target. Stationary noise (brown, white, mains hum) improved by 12 to 16 dB at 0 to 5 dB SNR in the same check. Use Mix, or Audio repair, when other people are talking in the clip.
- **First use downloads 8.6 MB of model** (plus a 12.6 MB WASM runtime) from the app's own origin; the service worker is set up to cache both so later runs need no network; offline use after a first run was not tested end to end. The model files are committed in `apps/web/public/models/deepfilternet3/` (licence and checksums in its README).
- **The preview plays the original until the enhancement is ready.** A 10 minute clip should take about 35 seconds on an Apple M2 Pro (about 17 times realtime with one WASM thread, nothing on the main thread; extrapolated from a measured 60 s clip); slower machines take longer. Playback continues meanwhile and the enhanced audio is swapped in with a 20 ms crossfade. An export waits for the job, and fails with the reason (rather than silently exporting the original) if the model cannot be loaded.
- **Preview and export agree, but the model may run twice.** Both use one cached job keyed by the sample content. The preview and the export decode a file with different decoders (the export upmixes mono to stereo through ffmpeg at -3 dB), so their buffers differ and the model runs once for each (for a long clip, twice the work). The network is fed the clip at a fixed level (RMS -20 dBFS) and the result is scaled back, so the two runs give the same samples up to rounding (residual below -90 dB in `enhance-quality.test.ts`). A side effect: very quiet voices are enhanced as well as normal ones.
- **Sources over 180 s need a worker.** The main-thread fallback (browsers without module workers) refuses longer sources; the normal worker path has no length limit apart from memory (the enhanced copy is as large as the decoded source: 230 MB per 10 minutes of stereo).
- **Speech / Background balance is a remix, not a separation.** "Background" is the original minus the enhanced signal, sample for sample (the enhancement is aligned with its source: same length, no delay). It therefore contains everything the network took out, including parts of the voice it attenuated or damaged, and the small level changes of the model's fixed working level, not only the room tone. 100 (the default) is speech only and renders exactly like an effect saved before the control existed (the balance is not stored at its default); 50 is the original mix; 0 is background only; Mix still blends the result with the original on top. Moving it never re-runs the model (`enhance-cache.test.ts`, and `e2e/reduce-reverb.spec.ts`: the model files are fetched once across three balances, speech plus background reconstructs the original below -160 dB). The background is not cleaned up or denoised further, and the control belongs to Enhance Speech: it adds Enhance Speech (Mix 100) to a clip that has none.
- **Stereo.** Identical channels are enhanced once; different channels are enhanced separately, so the stereo image of a noisy two-channel recording is not preserved exactly. Surround (5.1) sources are enhanced channel by channel.
- **No desktop main-process path.** Measured with the same code: native onnxruntime-node ran 60 s of audio in 3.07 s and the WASM runtime in 3.28 s (19.6 and 18.3 times realtime), because the STFT and feature code in TypeScript is as large a share as the network, so a native sidecar would not be faster and was not built.
- **Enhance Speech is a clip effect, not a rack effect:** it cannot be placed on a track or bus (hosted Audio Unit and VST3 plugins can, see "Plugins on track and bus racks"), and a muted video clip hands the effect to its linked audio clip.
- **Preview-only A/B** ("Hear Original") is stored on the effect (`previewBypass`, as for Noise Reduction) and is saved with the project; the export ignores it.
- **Agent tool**: `enhance_speech` adds, changes or removes the effect; it does not wait for the model to finish (the export does).
- **Verified in Chrome only.** The web e2e (`e2e/enhance-speech.spec.ts`, dev server and production build, software GPU) is the end-to-end check. The desktop app serves the same bundle and the model and runtime files from `app://` (`models/deepfilternet3/`, `ort/`; `protocol-paths.ts` already maps `.wasm` and `.mjs`), but it was not run with Enhance Speech, and Safari and Firefox were not tried. Cold start in the browser (model download from localhost, WASM start, then a 10 s clip) took 1.8 s; the first job of a session is slower on a real network because of the 21 MB of downloads.

## Reduce Reverb

Clip menu > Audio: Reduce Reverb, the clip right-click "Reduce Reverb", the Audio tab > Reduce Reverb section (Amount 0 to 100, default 60; Sensitivity 0 to 100, default 50) and the `reduce_reverb` agent tool add a "reduceReverb" clip audio effect. Two stages, both on the whole decoded source in a worker, cached per source and setting: weighted prediction error (WPE) dereverberation of the speech band (up to 8 kHz; a per-bin linear predictor over the frames 3 or more earlier, fitted to the recording itself, no room parameter) and a statistical late-reverb spectral stage (Lebart / Habets style: exponential-decay tail model, blind RT60 estimate from free decays after word and syllable ends, decision-directed Wiener gain with a floor and smoothing). The order is spectral repair, Reduce Reverb, Enhance Speech, hosted plugins, the live chain.

- **What was measured (and what it is not).** `reverb-quality.test.ts`, 10 s of public-domain read speech at 48 kHz convolved with synthetic exponentially decaying noise rooms (RT60 0.3, 0.8, 1.5 s; direct-to-reverberant 0 and 5 dB), real DeepFilterNet3 weights, Amount 60, Sensitivity 50, dry speech as the reference. SI-SDR in dB, input / Enhance Speech alone / Reduce Reverb alone / Reduce Reverb then Enhance Speech: RT60 0.3 s: -1.1 / -0.3 / 0.9 / 1.2 (DRR 0) and 4.1 / 4.4 / 5.8 / 5.7 (DRR 5); RT60 0.8 s: -1.0 / 0.7 / 2.4 / 2.7 and 4.1 / 5.3 / 6.9 / 6.8; RT60 1.5 s: -0.8 / 1.6 / 2.6 / 3.2 and 4.3 / 6.2 / 7.3 / 7.4. Clarity C50 (of the least-squares effective response of dry-to-output, a proxy for a time-varying system) rose by 3.1 to 7.4 dB with Reduce Reverb alone against -0.7 to +3.1 dB for Enhance Speech. These are synthetic rooms (a diffuse exponential tail), one speaker and one recording; no real room, no real-world recordings and no listening test were involved.
- **Enhance Speech still wins on the pauses.** DeepFilterNet3 treats the reverb tail in a pause as noise and gates it: the level of the pauses 60 to 160 ms after speech stops fell by 16 to 23 dB with Enhance Speech, 4 to 12 dB with Reduce Reverb alone and 11 to 25 dB with both, at the price of speech-frame level (-1.2 to -2.7 dB for Reduce Reverb alone, -2.1 to -5.2 dB with Enhance Speech after it, -1.9 to -4.6 dB for Enhance Speech alone). Reduce Reverb on its own leaves a quieter but audible tail in the pauses; on its own it is the better choice for SI-SDR and clarity, with both for a noisy roomy recording.
- **Why two stages.** Measured alone at Amount 60 (RT60 0.8 s, DRR 5 dB): WPE gave SI-SDR 7.1 dB but lowered the pauses by only 2 dB; the spectral stage lowered them by 12 dB but gave 4.3 dB and 29 percent more spectrogram blips than the input (WPE alone: 17 percent). WPE is not an estimate of the room and is the larger share; the spectral stage cleans the pauses and is scaled to 35 percent of Amount.
- **The blind RT60 estimate is rough.** It reads about 0.4 s for a 0.3 s room, 0.7 to 0.9 s for 0.8 s and about 1.0 s for 1.5 s on this speech (short pauses leave few free decays). It only steers the spectral stage; with too little evidence (a steady tone, a continuous voice) it falls back to 0.45 s, says so in the inspector and uses the stage at reduced strength. WPE does not use it.
- **Limits of the method.** It removes late reverb, not early reflections (the first 50 ms are kept on purpose), so a boxy room stays boxy. WPE only sees about 0.28 s of earlier frames and only the band to 8 kHz, so a 1.5 s room is reduced, not removed (SI-SDR +3.0 to +3.4 dB of the +4.8 dB that removing everything after 50 ms would give). Strong settings thin the voice and add fluttering: the isolated-blip count in the pauses (a musical-noise proxy) was 11 to 34 percent above the input's at Amount 60 and 25 percent at Amount 100 for RT60 0.8 s. Music, singing and anything that is not a voice in a room is treated like speech. A dry recording passed through it at defaults keeps SI-SDR 14.7 dB against itself and loses 0.9 dB of level.
- **Peak headroom and low Amount.** The result never peaks above the source's own peak: a 4 ms look-ahead gain limiter (not a clip, the same gain on every channel, untouched samples bit-identical) takes the gain down around an overshoot, which the stages produced on loud or hard-clipped input (peak ratio up to 1.42 before). The spectral stage's gain floor (6 dB plus 22 dB x its strength) scales with Amount below Amount 29, so Amount going to 0 converges to the identity: the error against the input was -52 dB at Amount 0.1, -34 dB at 1, -22 dB at 5 and -12 dB at 20 (4 s of the 0.6 s room). Amount 0 is bit-identical. The cache key's model id is `reduce-reverb-2`, so results cached with the old floor are not reused.
- **Cost and latency.** About 10 times realtime on one thread of this Apple silicon Mac (a 10 minute clip is about a minute), no model download. Each Amount or Sensitivity change is a new job per source and setting: the clip's own older, now unused setting is cancelled, but two clips of one file with different Amounts each keep their own job and both finish (at most 2 jobs run at once, the rest queue); the preview plays the unprocessed audio until it is ready and swaps with a 20 ms crossfade, the export waits and fails with the reason rather than silently exporting the reverberant audio. The processed copy is as large as the decoded source. The main-thread fallback (browsers without module workers) refuses sources over 120 s. Long sources are processed in 30 s blocks with their own filters and a 20 ms crossfade; a test checks there is no step at the joins.
- **Identical results, preview and export.** The processing is deterministic and a function of power ratios only, so a quieter decode of the same file gives the same result scaled (residual below -70 dB), and the preview's samples are bit-identical to the export's (`audio-engine.render-integration.test.ts`; -93 dB residual through the real Chrome mixdown in `e2e/reduce-reverb.spec.ts`).
- **Not done:** a stereo-aware or multichannel WPE (each distinct channel is processed alone; identical channels once), a per-band RT60, a rack (track or bus) version, real-time processing, and a before/after switch (Reduce Reverb has no "Hear Original"; toggle the effect). Verified in Chrome only; the desktop app and other browsers were not run with it.
- **Agent tools** (`reduce_reverb`, `set_speech_background_balance`, in the lazily loaded audio group) each make one undo step however many clips they touch and do not wait for the jobs. The existing Audio repair "DeReverb" (a fixed-RT60 spectral subtraction, live) is unchanged.

## Project Manager

File > Project Manager (desktop app only) collects or consolidates the chosen sequences into a new project folder. What it does not do, and where it differs from Premiere:

- **Image sequences:** the option "Convert image sequences to clips" is shown on and locked. OpenReel bakes an image sequence (CinemaDNG, numbered stills) into a video clip at import, so a project never holds one and there is nothing to convert.
- **Audio conform files:** OpenReel does not write conformed-audio (.cfa) files, so "include audio conform" cannot copy any. The option "Conform audio to 48 kHz PCM" instead writes the sound of every transcoded file as 24-bit 48 kHz PCM (AAC at 256 kbit/s in an H.264 MP4 keeps its codec and is resampled to 48 kHz only).
- **Match source is a codec family, not the exact profile:** ProRes sources become ProRes 422 HQ (the profile is not read from the file), DNx sources become DNxHR HQ, and anything else (H.264, HEVC, MPEG-4...) becomes high-quality H.264 (CRF 14, capped). 10-bit sources written as DNxHR use the 8-bit 4:2:2 profile. Interlacing and field order are not carried through a transcode. Rotated phone footage comes out upright (the rotation is applied, not kept as a flag).
- **Hosted plugin tails and pre-roll in trimmed files:** a reverb or delay tail of a hosted audio plugin (Audio Unit or VST3) that runs past a clip's out point is not kept by trimming, because the file is cut at the out point plus handles and a tail cannot be known without rendering the plugin. The trimmed file also changes the plugin's pre-roll near the trim start: the plugin starts from silence at the new start of the file instead of having processed the earlier source, so a reverb, delay or compressor that was already ringing or warmed up at the in point sounds different there until its state settles.
- **Trimmed files:** a file keeps at most 48 stretches (the closest gaps merge first) and gaps under one second are kept rather than cut. A multicam angle keeps one stretch. Data keyed to source time other than clip and master markers (a stabilization analysis, motion-tracking paths, transcripts stored per media) is not shifted; re-run those on a trimmed project. A trimmed copy has no footage outside the handles, so slipping a clip further than the handles cannot reveal more.
- **Render files** are copied only for an untrimmed project (trimming moves every frame). They are restored into the render cache when the project is opened and then validated by the render cache's own content hashes, so a changed file path or size can make them re-render; they are an optimisation, not a guarantee.
- **Proxies** are copied with the media or, when the media is trimmed, cut with the same ranges and re-encoded in the proxy's codec. Preview twins are cut the same way.
- **What is not copied:** media that exists only inside the app (a recording not saved to disk, generated assets without a file) and offline media are left out with a warning and stay as they were in the copy; fonts, LUTs, installed audio plugins (VST3 / Audio Units; the copy keeps each effect's saved state and automation and needs the same plugin installed) and caption files are not collected. The new project gets a new id.
- **Moving the folder:** the project records absolute paths. After the folder is moved, opening the project finds files in the `Media` folder beside the project file by name; proxies and anything else use Relink from Folder.
- **Disk space:** the estimate for ProRes and H.264 is a typical size from Apple's published data rates and the encoder's rate cap; real footage can differ (within 30% for ProRes and DNxHR HQ in the tests, H.264 varies with content and is capped at 0.8 bits per pixel). The run refuses to start when the free space is less than 1.25 times the estimate.
- **Not run:** Windows and Linux builds, sources over 1.5 GB reopened through the relink path (the existing reconnect reads a non-native file into memory), and real camera footage were not exercised; the tests use generated ProRes and H.264 sources.

## Media Browser and XMP metadata

- **Camera-card layouts follow the public folder conventions and were tested on generated structures, not on real cards.** The fixtures are ffmpeg-made clips arranged as Sony XAVC S, Canon XF, Panasonic P2, AVCHD and GoPro cards. No card from a real camera was available, so vendor variations (Canon XF-AVC naming, Sony XDCAM sub-folders, P2 files written by older firmware) may show as plain folders until the layout is added; "Folders" on the card banner always shows the raw tree.
- **How spanned recordings are found.** P2: the `Previous` / `Next` references in each `CONTENTS/CLIP/*.XML` (the element names are from the published P2 layout, not checked against a real card). AVCHD: the `NNNNNM2TS` clip names a playlist (`PLAYLIST/*.MPL`) lists; with no playlist folder, consecutive stream numbers whose earlier file is at least 1.9 GB are treated as one recording (a heuristic). GoPro: chapter numbers in the file name (`GH01`, `GH02`..., `GOPR` / `GP01`...). Sony XAVC and Canon XF clips are separate files and are not joined. A playlist that lists unrelated clips together would join them.
- **A joined clip is a new file in the app's cache** (`media-browser/joined` in the user-data folder), built once with stream copy and reused; the camera files are only read. The project references that cached file, so clearing the folder takes the media offline. Panasonic P2 audio (one MXF per channel) is muxed into the joined file, which was tested with PCM audio files standing in for P2 audio MXFs (ffmpeg cannot write audio-only MXF) and DV video.
- **Import goes through the main process into memory.** Files over 1.5 GB are refused with a message (use File > Import for those). Previews are a 360p H.264 stand-in of the first 5 minutes, not the original, and do not apply the camera's colour or pixel-aspect handling. The preview is not interlace-aware.
- **Web: reduced.** Needs a browser with `showDirectoryPicker` (Chrome, Edge). No hover scrubbing, no joining (the segments of a spanned clip import as separate items and the preview plays the first one), no sidecar writing, thumbnails only for formats the browser decodes, and no volumes list.
- **XMP reads Dublin Core and the xmpDM log fields only** (`dc:description`, `dc:subject`, `dc:title`, `dc:creator`, `dc:rights`, `xmpDM:scene`, `shotName`, `takeNumber`, `good`, `logComment`, `tapeName`); other properties in a sidecar are kept untouched when the sidecar is updated, but are not shown. Camera-vendor metadata (Sony NRT XML, Canon `.CIF`, P2 XML) is not read as XMP. Extended XMP (packets split across several JPEG segments) is not read. `xmpDM:takeNumber` is an integer in the XMP spec; a non-numeric take such as "2B" is still written there and strict readers may drop it.
- **Sidecars are named `<clip>.xmp` next to the media**, the Adobe convention for Premiere and Bridge; the same-name sidecar of a joined clip is not written (the first camera file's sidecar is the one read at import). Editing in the app never rewrites embedded XMP, so a clip that has both reads the sidecar's values over the embedded ones.
- **Not carried into some exports.** EDL locators and chapters text carry no metadata; SRT, TTML and the broadcast caption formats have nowhere to put it. Marker CSV columns follow the clip under the marker on the lowest video track. Premiere may not accept the extra CSV columns when re-importing.
- **Verified only in the desktop app on macOS (arm64)** with the Electron e2e (`pnpm --filter @openreel/desktop test:media-browser-e2e`); the web reduced version is covered by component tests with a mocked File System Access API, not by a real browser run.

## Audio plugins (Audio Unit and VST3 host, macOS desktop)

- **macOS only, Audio Units and VST3.** Two helpers speak one protocol (`apps/desktop/src/shared/plughost-protocol.ts`): `openreel-plughost` (Swift, AUv2 and AUv3 effects through AVAudioUnit / AUAudioUnit) and `openreel-vst3host` (C++, VST3 effects through the Steinberg VST3 SDK 3.8.1, MIT). VST3 bundles are found in the standard folders (`/Library/Audio/Plug-Ins/VST3`, `~/Library/Audio/Plug-Ins/VST3`, the Windows `Common Files\VST3` and `%LOCALAPPDATA%\Programs\Common\VST3`, Linux `~/.vst3` and `/usr/lib/vst3`) plus any folder in `OPENREEL_VST3_PATH`, by a folder walk that runs no plugin code, and validated in a helper process of their own. Windows and Linux: the VST3 helper's source and build script contain those paths, but nothing was compiled or run there, and no release workflow step builds them, so the Audio plugins panel reports that plugin hosting is unavailable there; a build without `openreel-vst3host` (no CMake, offline first build) lists VST3 bundles as "found but not hostable in this build".
- **VST3 scope.** Audio effects only, the first effect class of a bundle, one main stereo/mono (or accepted multichannel) bus in and out, 32 bit float, no sidechain or other auxiliary buses, no MIDI/events, no instruments, no program lists or units, host tempo fixed at 120 bpm 4/4 for plugins that read the process context. Parameters are the controller's normalized 0..1 values (the plugin's own display text is shown only at the moment the parameter list is read). Hidden, read-only and program-change parameters are not exposed. The VST3 helper was verified only against the SDK's `adelay` example (and broken builds of it) built in the test setup, on Apple silicon; no commercial or third-party VST3 plugin was tried, so plugins that need a particular host behaviour (a view with `IPlugFrame` quirks, bus layouts other than the main one, plugins that must run on the main thread) are untested. The x64 helper builds (`--all`) and answers `hello` under Rosetta; no x64 plugin was loaded. VST3 libraries are never unloaded inside the helper.
- **Test and packaging caveats.** The SDK is fetched at build time (network, SHA-256 pinned); an offline first build skips the helper. The helper's signing and notarization inside the app bundle was not run (it inherits the app's entitlements including `disable-library-validation`). On macOS 27 inside agent worktrees a freshly built helper (Swift or C++) was killed on its second launch; the tests then ran against copies outside the worktree via `OPENREEL_VST3HOST_PATH` / `OPENREEL_PLUGHOST_PATH`.
- **A clip plugin is an offline, whole-source effect, not a live insert** (track, bus and master racks can play live in the preview, see "Live plugin inserts" below). On a clip, like Enhance Speech, the plugin renders the clip's decoded source once in the helper, and the preview and the export play that cached result. Consequences: the preview plays the unprocessed clip until the render finishes (about 95 times realtime for AUDelay and about 50 times for AUMultibandCompressor over the pipe on an Apple M-series Mac; a 10 minute clip is ready in 6 to 12 s); the whole source is rendered even when only a few seconds are used (cost and memory scale with the media, not the clip); a parameter or state change re-renders from that plugin on; the cached copy is as large as the decoded source. Clips do not stream through the plugin at all, and no live input does either, so live monitoring and recording through plugins are not possible.
- **Parameter automation is block rate.** Keyframes become lanes sampled at 512 frames (10.7 ms at 48 kHz); eased segments are sampled every 10 ms. It is per source time: speed ramps (speed keyframes) and freeze frames are not accounted for (a constant speed and a reversed clip are). Parameters are set before each block, so a plugin that smooths its own parameters will smooth over more than one block.
- **Latency is compensated exactly inside the render** (the helper feeds the plugin the latency's worth of extra silence and drops that many leading samples), so a lookahead plugin stays aligned with the clip and with other tracks. A plugin that reports its latency wrongly is aligned wrongly; the reported value is shown in the card. Plugin tails after the end of the source are cut (the source length is kept).
- **Channels.** The plugin is run with the source's channel count (mono, stereo, 5.1 when the plugin accepts them). A mono clip on a stereo-only plugin is run dual-mono and folded back to mono, so a stereo-widening plugin loses its width on mono clips. The plugin sees the decoded source at its own sample rate before the clip's channel map, speed and fades.
- **Crash isolation is process isolation, not a security sandbox.** A plugin that segfaults, hangs (15 s probe, 10 s per audio block) or writes garbage on the pipe costs one helper process; the editor keeps running, a crash or hang while scanning or rendering puts the plugin on the blocklist (`plugin-blocklist.json` in the user data folder; Unblock in the panel; a new plugin version gets a fresh chance) and an export that needed it fails with the reason instead of exporting different audio. The helper runs with the app's privileges: a malicious plugin can read your files. Plugins are loaded in the helper in-process (`.loadInProcess`); Apple's out-of-process AU hosting was not used.
- **Missing plugins are reported on open and bypassed.** The effect stays in the project with its state chunk and values, so installing the plugin later restores the sound; the export of such a project works but does not contain the plugin (a warning toast names the plugin). The report fires when the open project changes (a different project id), so reopening the same project in the same session does not repeat it. On the web build every plugin is reported as needing the desktop app.
- **Plugin window.** The plugin's own editor (Apple's generic view for an Audio Unit without one; a VST3 without an editor reports it) opens in a separate helper process; parameter edits are not applied to the clip live: when the window closes, its state chunk and values become one undoable edit. State that a plugin keeps outside its saved state (not in `fullState`) is not captured. The window was verified on Apple's generic views and a minimal test editor for the VST3 `adelay` example (a label, a simulated edit); no third-party custom plugin UI was available to test; it needs a display.
- **Not built:** sidechain, MIDI and instrument plugins, host tempo sync, presets browsing, agent tools for plugins, and the portable `openreel-edit` JSON format does not carry plugin effects. Not verified: any third-party Audio Unit or VST3 plugin (Apple's built-ins and the SDK's adelay example were tested), the e2e ran on Apple silicon only (the x64 helper builds with `--all` in the release workflow and, under Rosetta, lists and probes the built-in plugins, but no render or e2e was run with it), signing and notarizing the helper inside the app bundle (it inherits the app's entitlements, including `disable-library-validation`, in `electron-builder.yml`; not run).

## Live plugin inserts (macOS desktop)

Track, bus and master racks stream through their plugins while the preview plays (Live preview, the default; Rendered switches a rack back to the cached render). Design, numbers and tests: [audio-plugin-hosting.md](audio-plugin-hosting.md#live-inserts-preview-of-track-bus-and-master-racks). What it does not do, and what to expect:

- **Preview only.** The export, the Loudness panel and the stems always use the offline render, so a plugin whose output differs in realtime mode from its offline mode sounds different live than in the file. For the Apple built-ins and the VST3 SDK's `adelay` live equals offline sample for sample (measured); no third-party plugin was tried, so that is not known for them.
- **Latency is added, not hidden.** A live insert delays the signal by a jitter buffer (at least 20 ms of transport: 21.3 ms at 256 frame blocks) plus the chain's reported latency, and every other track is delayed to match, so playback stays aligned with the picture (sources start early, exactly as for built-in latent effects); only a monitored live input would hear the delay. The residual misalignment after compensation is at most half a frame (delays are whole frames); a plugin that reports its latency wrongly is aligned wrongly, as offline.
- **Dropouts are possible and are counted.** If the main process or a helper is stalled for longer than the jitter buffer, that stretch plays as the time-aligned dry signal with a crossfade (never a click, never silence), is counted in the rack panel, and the stream recovers by itself. In the four-insert benchmark under heavy machine load that was 0.07 to 0.6 % of blocks; on an idle machine the real-app tests had none. A larger block size (512) trades latency for safety. There is no automatic switch to the cached render on dropouts (a mid-playback cut would be worse).
- **CPU.** About 17 % of one core of the main process and 2 to 4 % of a core in the helper per insert at 256 frame blocks (measured, not optimised); the worklet's own cost was not measured. Racks can play live at most 12 at a time; further ones play rendered.
- **A crashed or hung helper mutes that insert.** It plays dry (aligned) until playback stops, the panel shows the reason and a Retry; then the rack's rendered version plays. Nothing else is affected.
- **Parameter automation is block rate and approximately aligned.** Lanes are evaluated per block at the timeline time the stream was started at (play, seek and loop restart the stream), so a keyframe can be off by the playback latency (about 20 to 30 ms) and the block size. Scrubbing and auditioning (nothing running the transport) pass a live rack's signal through unprocessed and undelayed.
- **Plugin windows.** Edits made in a plugin's own window reach the live plugin when the window closes (as for renders), not while dragging; only the panel's sliders are live.
- **Reopening.** Adding, removing, reordering or enabling a plugin, or changing the block size, reopens that rack's session (about 0.1 s; the old insert keeps playing until the new one is ready). Sessions are reopened after a helper crash only on Retry.
- **Not live:** clip plugins, 5.1 sequences (bypassed), the web build (no helpers), Windows and Linux (no helper has run there). The portable `openreel-edit` format and the agent do not carry the Live/Rendered switch (the agent has no plugin tools at all).
- **Transport.** The audio goes worklet -> MessagePort -> main process -> pipe -> helper and back; a zero-copy shared-memory path was not built (see the design note). `LiveRing` exists and is tested for it.

## Plugins on track, bus and master racks (macOS desktop)

Hosted Audio Unit and VST3 plugins can sit on a track, a submix bus or the master bus (mixer strip > Plugins, the Master strip included), in addition to a clip. What they do and do not do:

- **A stem for the export, and for the preview when the rack is set to Rendered.** The track's (or bus's) summed signal before its built-in rack, fader, pan and sends is rendered offline over the whole timeline, run through the plugin chain in the helper (latency compensated, parameters automated from the rack's keyframes) and cached by the exact inputs; the preview and every export play that same buffer. Until the first render of a changed stem finishes, the preview plays the track or bus dry. Cost and memory scale with the stem length plus a fixed 2 s tail, not with what is played, and the cache keeps the 3 most recent stems.
- **When a stem is invalidated.** A track stem is keyed by that track only: its clips (position, length, speed, source, clip effects, volume and fades), its mute / solo state and its plugin chain. An edit on another track, including a multi-clip ripple speed that lengthens or shortens the timeline there, leaves it alone (its window ends at its own last clip plus the tail, not at the timeline end). A ripple that moves this track's clips (it is selected, or it is sync-locked and follows the ripple) changes its clip timing and re-renders it. A bus stem sums whatever feeds it and is keyed by the whole routing, so any audio edit anywhere in the project re-renders a bus stem; the live preview does the same for projects with a bus rack. Editing one plugin re-renders from that plugin on.
- **Background-task panel.** Each stem render is a row titled "Plugins on Track <name>" or "Plugins on Bus <name>" with progress, Cancel and Retry; a clip's own plugin render keeps the title "Audio plugin render". The rendering of the dry stem before the plugins run (the mixdown of the track) has no row of its own.
- **Limits.** Stereo and mono sequences only: in a 5.1 sequence every track and bus plugin is bypassed and reported (the plugins would see six channels). Up to the same number of plugins per rack as per clip. A muted, or not-soloed, track or bus is not rendered at all. Plugin tails longer than 2 s past the last clip are cut. A missing, blocked or failing plugin follows the clip rules above (bypassed and reported when missing, a loud export failure when it fails). The plugin window, parameter automation (track keyframes, block rate) and Hear Dry work as on a clip.
- **Verified with.** Apple's AUDelay and AULowpass in the real Electron app (`plughost-track-racks-electron.test.ts`), the web e2e with a stand-in backend (`track-plugin-racks.spec.ts`), and the Steinberg SDK's `adelay` VST3 example through the real VST3 helper at the stem level (`plughost-track-rack-vst3.integration.test.ts`: the format spawner picks the VST3 helper, the stem equals adelay's analytic delay sample for sample, a second resolve is a cache hit, a moved clip re-renders). The full app (mixer panel insert, automation, a real WAV export, the preview path) is run with the same VST3 on a track rack and on the master rack by `vst3-racks-electron.test.ts` (see the master section below). No third-party plugin was tried on a rack.

### Master rack

- **Where it sits.** Premiere's order: tracks (clips, clip effects, track plugins, track rack, pan, fader, sends) and buses sum, then **master plugins**, then the master fader, then the built-in master rack, and only for an export, **loudness normalisation** and the **true-peak limiter**. Normalisation therefore measures the mix after the plugins (a plugin that adds 6 dB makes the planned gain 6 dB lower), and a plugin on the master can never push an export past the true-peak ceiling the user chose. The Loudness panel and the stems/stem-isolation exports also follow this: stems are the pre-master parts, so they do not contain master plugins.
- **The master stem is the whole mix.** The whole summed mix (every audible track and bus with their own plugins already applied, no master fader or built-in master rack) is rendered offline over the whole timeline plus a 2 s tail, run through the helper (latency compensated, automation baked from the master rack's keyframes, in timeline seconds) and cached by the full-mix fingerprint plus the chain signature. The preview and every export window play that same buffer, replacing all the tracks, through the master fader and built-in master rack. Any audio edit anywhere re-renders the master stem (it is the whole mix); a master fader, master rack or loudness edit does not. While it re-renders the preview plays the mix dry. A master stem rendered while an upstream track or bus plugin was bypassed (not installed, no host) is not cached, so installing the plugin is picked up.
- **Missing or failing plugins.** A missing, blocked or host-less master plugin is bypassed, reported ("Plugin missing", the track-and-bus report names "Master") and kept in the project; if every master plugin is bypassed the track and bus racks still render normally under it. A plugin that fails while rendering fails the export. 5.1 sequences bypass the master plugins like every rack plugin.
- **UI and history.** The Master strip has the same Plugins button and lazily loaded panel as a track; the stem renders as "Plugins on Master" in the background-task panel. Insert, values, reorder, bypass, window edit and each keyframe are one undo step each (`audioPluginRack/set` with the reserved target `__master__`, stored as `timeline.masterPluginRack`, per sequence). The master rack is not carried by interchange formats (the import/export report lists it as dropped) and the agent has no tool for it.
- **Limits.** Memory and render time scale with the whole timeline plus tail (measured in the Electron e2e on Apple silicon with the SDK's adelay: a 4 s stereo project mixes down in about 1.05 s without the plugin and 1.1 s with a master plugin, the helper pass itself taking tens of milliseconds, so the cost at that length is the mix, not the plugin; a long project holds its whole mix in memory twice, once dry and once processed, and the cache keeps three stems). Nested sequences use their own racks only: the outer master plugins process the nested mix as part of the outer mix, a nested sequence's master plugins are not applied (the existing master-rack rule). Tails longer than 2 s are cut.

## Multi-clip speed and ripple

Clip > Speed/Duration and the Rate Stretch tool act on every selected clip, optionally rippling the rest of the timeline, as one undo step.

- **Speed ramps and freeze frames are refused.** A selection that includes a clip with speed keyframes or freeze frames is not retimed; remove them first.
- **Duration is a combined length** applied as the same factor to each clip; it does not fit clips to a target gap.
- **Sync lock decides what else moves.** Sync-locked tracks open or close the same span, or the edit is blocked when they hold media inside it; locked tracks refuse the edit.
- **Timing numbers are from one machine.** On a 1000-clip sequence (2000 clips with linked audio) the ripple speed plan took about 200 ms before and about 16 ms now (Node), the store commit about 35 ms, and the click to a committed state about 4.3 s in the Vite dev server, which logs every re-rendered component. A production-build browser profile, and playback, scrub and export of a 1000-clip sequence, were not measured.

## Big selections on long timelines

- **Off-screen selected clips are not mounted** once more than 32 are selected (select all, a large marquee); at most 32 selected clips outside the viewport stay mounted. Drag, delete, copy/paste and the inspector work from the stores, so they cover every selected clip; anything that reads clip DOM elements for a big selection only sees the visible ones. Tested on a 1000-clip, two-track sequence in a production build (`e2e/timeline-select-all.spec.ts`); 3000-clip selection was measured for select-all, ripple speed and ripple delete only (`e2e/timeline-perf.spec.ts`), not for drag or delete.
- **Dragging a selection of 8 or more clips** uses one batched move per frame for media clips. Text, shape, SVG and sticker clips in such a selection get one timing update each, so a big mixed selection drags more slowly than a media-only one. A big selection dragged onto another track moves the dragged clip's track only, as before.
- **History size.** The undo limit (1000) counts undo steps. One step can hold thousands of entries (delete of 2000 clips), and a group is never split, so memory for a very large step is not bounded by the limit.
- **Paste of a big selection** is one `clip/addBatch` for the media clips (2000 clips: 169 ms in the production e2e, 13 s before). Text, shape, SVG and sticker clips in the clipboard are still pasted one by one after the batch (same undo step, same placement), so a big mixed paste is slower than a media-only one, and clip order inside a track is "all media clips, then overlays" rather than clipboard order (overlays live in their own lists, so this only shows in the pasted-ids order). A media clip whose media was removed from the library is reported as failed without creating the track it would have needed.
- **Nudge on a big selection** (Alt+Arrow, with the Ripple, Slip, Roll, Slide or Rate Stretch tool) moves the edit of every selected clip as one undo step. Ripple is planned in ONE pass over the timeline (`planRippleSelectionBatched`: the same bounds, frame rounding and floating-point additions as the one-edit-point-at-a-time planner, replayed on plain numbers, edits built once): select all on 2000 clips commits in about 320 ms in the production e2e (was about 2.9 s, 1.3 s of it planning; planning is now about 20 ms), and the result equals the sequential planner on 600 randomized projects plus the fixed equality tests. The batched planner only handles plain media clips on distinct unlocked tracks with no transitions, no text / shape / sticker / adjustment / motion items, no track groups and no sync-locked track outside the edit that holds clips; anything else (and any edit point that would fail) uses the sequential planner, whose cost grows with the number of distinct edit points (about 1 s per 1000 edit points at 2000 clips). Roll, Slide and Rate Stretch still use the sequential planner. Edit points that cannot move (locked track, source handle, a neighbour in the way, linked clips that are not aligned) are skipped and counted in the toast; Roll and Slide need a neighbour on the relevant side, and Rate Stretch cannot extend into a touching clip, so on a gap-less sequence only the last clip of each track moves. The , and . edit-point trims act on the single selected edit point only (there is no multi edit-point selection).
- **Remaining long tasks.** Ripple speed on 3000 clips is a 106 ms task on the first (cold) ripple of a session and 61-72 ms afterwards (5 runs, median 71 ms; before: 130 / 91 / 105 ms); ripple delete is 80 ms at most (98 before). A CDP trace showed the task is the click handler plus React's synchronous commit, not native layout (layout and style are about 4 ms); the commit now copies only the new items of a plan instead of both halves and then the inverse. The cold first ripple still sits just over 100 ms. The task budget in `timeline-perf.spec.ts` (120 ms) is asserted at 1000 clips only.
- **Desktop cold start compiles 52 chunks** (was 62, 50 before the smart-render and multichannel merges; budget 58, `traceCold.totalChunksCompiled`; 3 `perf:budget` runs, all 52: the two new ones are the lazily loaded `premiere-edit-commands` and `replace-fit` chunks, which the multichannel edit paths load on first use; the multichannel agent tool handlers are a lazy chunk too, the agent chunk is 902.4 KB raw). The 62 were the editor's static closure split by Rollup into a chunk per set of lazy consumers. Fixed in the source rather than by tuning: engines no first-paint path needs (subtitles, speech-to-text, templates, sound library, multicam) moved out of `engine-modules` into `optional-engine-modules`; the interchange engines and the spotlight tours (framer-motion) load on first use; the settings dialog mounts lazily; and the small `@openreel/ui` components the welcome entry does not use share one `ui-components` chunk (desktop build only) instead of each being folded into a lazy chunk (collaboration session, watch folders, plugin manager, tour) that the editor then pulled in. Eager bytes fell 6666 -> 6284 KB, `totalCompileCpuMs` 96 ms (budget 110; 102-107 before at similar load), `startupCpuMs` 96 ms (budget 200), `totalCpuMs` 435 ms (budget 540); no budget was changed. Limits: the entry chunk grew about 15 KB (it absorbs two small lazy chunks) and `ui-components` (26 KB) is on the welcome path; a manual chunk for the whole editor-shared closure and a larger `experimentalMinChunkSize` were tried and rejected (the first made the welcome screen import 4 MB, the second cost 10-13 % compile CPU). The 16 wall-clock budgets were not judged (machine load 15-18 against the 2.5 limit).

## Source monitor history and Reverse Match Frame

- **History entries remember each clip's In, Out and playhead.** History and playheads are kept in this browser's localStorage, keyed by project id: they survive reloads but are not in the project file, so they do not travel with the project to another machine or browser profile.
- **Reverse Match Frame** lists every instance of the source frame in the sequence (retimed, reversed and inside nested sequences) and Shift+F cycles through them. It matches by source and source time, not by comparing pixels; behaviour on clips with speed ramps or freeze frames was not specifically tested.
- **Clip markers** are written to OTIO (clip and master-clip markers, source time). The agent has `reverse_match_frame`, `list_clip_markers`, `add_clip_marker` and `remove_clip_marker`. Other interchange formats carry them as described under "Not carried into some exports".
- Covered by unit tests and `source-history.spec.ts`, `match-frame.spec.ts` and `clip-markers.spec.ts` on synthetic clips; not tried on a long real project.

## Time Interpolation (Frame Sampling, Frame Blending, Optical Flow)
- **Per clip, video clips only.** The setting is on the clip, not a sequence or export setting. Audio, images and text/graphics are unaffected. Clips inside a nested sequence take the path through the same decoder, but that was not tested, and the nest clip itself has no setting.
- **Export at another frame rate still holds sequence frames.** A 24 fps sequence exported at 60 fps repeats sequence frames; Time Interpolation only makes the in-between frames of a retimed or frame-rate-conformed clip at the sequence's own frame instants (`exportRenderTime` is unchanged). There is no Premiere-style "frame blend the whole sequence on export".
- **Optical Flow is an estimator, not magic.** It reads smooth motion well (the unit scenes: 31-43 dB against ground truth, 6.6-9.2 dB better than Frame Blending). It fails or degrades where the premise fails: unrelated content cross-dissolving (measured 18 dB against an exact blend of 54 dB: the flow invents motion; the confidence gate only softens this), fast motion beyond the pyramid (the flow is estimated at most 512 px on the long side at High, about 240 px at Low, so large displacements between two source frames can be lost; the limit was not measured, the unit scenes move 4-9 px per frame at 128-256 px wide), thin fast objects, motion blur, fire, water and smoke, repetitive textures, large occlusions (they fall back to a blend, so a ghost remains around fast-moving edges), and very flat footage. Premiere's own optical flow has the same families of artefacts but is not identical; this is not a claim of parity in quality.
- **Not scene-referred.** A clip with Frame Blending or Optical Flow renders on the 8-bit path (in HDR / ACES working mode it is treated like the other 8-bit-only clips, see the HDR notes above), and a stabilised clip (the stabilised render replaces the source) is sampled, not interpolated.
- **Real time depends on the GPU.** With WebGPU compute a 1080p frame is about 15 ms after the first of a pair at medium quality, plus decode and readback; without it (CPU reference) a frame takes about a second, so use Sequence > Render In to Out (the status bar shows Optical Flow red until it is rendered) before playing back. Playback of an unrendered Optical Flow clip on the CPU path will drop frames. There is no separate low-quality live proxy for an unrendered range: the preview always shows the real result, waiting for it.
- **Memory.** Finished frames are cached up to 192 MiB, decoded source frames 96 MiB and the flow of recent pairs 48 MiB, per tab; scrubbing across many different pairs at 4K recomputes more.
- **Readback.** Frames are read back to the CPU between decode, the GPU interpolator and the compositor (`getImageData`, `mapAsync`); this is the dominant cost for small clips and was not optimised away.
- **CPU and GPU agree within tolerance, not bit for bit.** Measured 74-84 dB PSNR (mean absolute difference at most 0.003 levels) on motion scenes and 57-58 dB (0.11 levels) on a fade at 256x144; summation order and `exp` differ. A project rendered on a machine with WebGPU and on one without gives frames that differ by that much (a level or less), not visibly.
- **Desktop native export.** The native (ffmpeg) export path does not do its own interpolation: ffmpeg `minterpolate` would not match the in-app result, so frames are still rendered by the one in-app renderer. A clip with Time Interpolation is never stream-copied by smart render.
- **Scene cuts output the nearer source frame.** When two consecutive source frames are a cut, Frame Blending and Optical Flow output the nearer source frame (t < 0.5: the earlier, otherwise the later) instead of a ghost or a warp, identically in preview and export and on the WebGPU and CPU paths (the decision is made once per frame pair before the backend split, `scene-cut.ts`). A cut is flagged only when the best-translation correlation, the flow confidence, and the motion-compensated luma error (or histogram distance) all say the pictures are unrelated. Measured on the unit-test set (`scene-cut.test.ts`: synthetic non-periodic pictures, ffmpeg testsrc2 and other lavfi sources, 32 cuts / 64 non-cuts including pans up to a quarter of the frame per frame, flashes, fades, dissolve steps, rotation and time-separated frames of one scene): 0 false positives, and the cuts missed are cuts between periodic sinusoid test pictures (they correlate with each other at some shift and share a tonal range). A picture with almost no luma contrast (a white flash frame, a black frame, a flat card, a fully clipped exposure) is never judged a cut, because a flash, a dip to black and a cut to a card look the same to the detector and blending toward such a picture reads as a fade; so a hard cut to or from a flat colour or black is interpolated (the earlier behaviour) rather than held. A cut between two very low-contrast shots of similar colour (luma standard deviation under about 0.05, about half of the cuts at 0.03 and most below it in a synthetic noise test) may also be interpolated. A pan of nearly half the frame per frame (outside the correlation search range) reads as a cut.
- **Tests that exist and ones that do not.** Unit: analytic scenes (translating textured square with occlusions, sub-pixel pan, rotating disc, fade to black, unrelated cross dissolve), exact blend weights, determinism, quality levels, cache hits and flow reuse, undo / redo, save and reload, legacy Smooth Slow Motion. Browser: GPU against CPU on the same scenes, 1080p timing, a 25% clip scrubbed, rendered in the engine in preview and export mode, exported and compared frame by frame, on the GPU and on the software (no WebGPU) path; Render In to Out. Not run: a real-footage quality review (no camera footage of fast motion was used, only synthetic scenes and the testsrc2 fixture), Windows and Linux, discrete GPUs, 4K timing.

## Morph Cut

Morph Cut (Dissolve category, `morphCut`) hides a jump cut inside one continuous shot. What it is and how far it goes, honestly:

- **Not verified on real talking-head footage.** It was built and calibrated against analytic scenes (a textured face-like ellipse with eyes, mouth and hairline over a textured wall, with a small head translation, scale and rotation and a blink, plus whole-frame re-framing) and against the e2e fixture's test pattern; no real interview footage was available. The quality gate (`MORPH_CUT_CONSTANTS`) was tuned on those, so it may be too strict or too lax on real faces, hair, glasses, hands and busy backgrounds. The gate numbers are in the transition's status line (confidence) to make that visible.
- **No face model.** The brief allowed face landmarks only if a model was already bundled. The editor bundles none (MediaPipe face detection exists in `apps/studio` only, a separate app), and a heavy model was not added. The morph is purely photometric: a global similarity from feature matches, then dense optical flow. A mouth or eyelid that changes shape between the two sides is blended where the flow is not confident, not landmark-guided.
- **Only the two frames at the cut are analysed.** The analysis reads the outgoing clip's frame at its out point and the incoming clip's frame at its in point, at project size, and applies the resulting displacement field to the live frames of the whole span (the outgoing clip's frames before the cut, the incoming clip's after it). The app holds a clip's first and last frame for the rest of a transition (it does not read past the trim), so the handle frames Premiere also analyses are not used. Where the picture moves a lot inside the span the field is approximate, and a very large move inside the span is not corrected.
- **The pose difference has limits.** The global alignment is a similarity (translation, uniform scale 0.6 to 1.7, rotation up to 35 degrees), found from patch-matched corners with RANSAC. There is no homography and no perspective, and the corner matching is not rotation or scale invariant beyond a few degrees and about 10 percent per patch. Beyond what the pyramid flow can follow (it tolerates tens of pixels at the 256 to 512 px analysis size), the gate fails the cut and it stays a cross dissolve.
- **Fallback, never a broken warp.** Until the analysis finishes, when it failed ("Morph Cut could not align these shots", with the reason in the log), when the frames cannot be read, when the media has no bytes, and when the render frame's aspect ratio differs from the analysed one by more than 2 percent, the transition renders as the ordinary cross dissolve. A failed analysis is reported on the transition (inspector, agent `get_morph_cut_status`); the timeline clip itself shows no badge.
- **Analysis is not saved.** The finished field is cached in memory by footage identity, reference times, project size and detail setting (so undo, redo, duplicates and re-adding reuse it), but it is not written to the project: after a reload each Morph Cut analyses again in the background (about 0.1 s on the GPU and 0.2 to 0.7 s on the CPU at 1080p) and is a cross dissolve until it finishes. An export waits for it, so an export is always the morph.
- **Analysis sees the source, not the clip's look.** It reads decoded source frames before the clip's own transform, crop, effects and colour. If the two sides differ in those (one is scaled up, one is graded differently), the field is computed for the unadjusted frames; for the usual case of two parts of one clip with identical settings this does not matter.
- **Real time depends on the GPU.** Rendering a morph frame at 1080p was measured at about 11 ms on the GPU and about 860 ms on the CPU reference (Chrome on an Apple-silicon laptop); a 1 s transition (30 frames) is therefore about 0.4 s of work on the GPU and about 26 s on the CPU, plus decode. Without WebGPU, play the span after Sequence > Render In to Out, or expect dropped frames.
- **Eyelids and mouths do not morph.** A blink or a mouth that opens is a local change, not motion: where the match confidence is low the two sides are blended (a half-closed eye at the middle of the transition), as Premiere shows without face landmarks. The measured quality on the synthetic blink case is a gain of about 3 dB over a cross dissolve away from the eyes, and the eye region itself is better than a dissolve by about 3.7 dB.
- **Needs a cut between two clips.** A clip's own fade in or out (a clip-edge transition) cannot be a Morph Cut: the bridge refuses it and the inspector does not offer it. The transitions panel card previews as a cross dissolve and is marked "Needs analysis", because a card has no pair of related shots to analyse.
- **Interchange.** Premiere XML and OTIO carry the name "Morph Cut" (Premiere analyses the cut itself on import; OpenReel's field is never exported), FCPXML, EDL and AAF write a cross dissolve; every format reports the transition as approximated.
- **Smart render.** A clip with any transition is re-encoded, so a Morph Cut re-encodes the whole of both clips it joins (the existing rule), not just its span.
- **Pre-existing export bug fixed on the way.** With both sides of a transition cut from one file (every jump cut) the export decoder's shared canvas made the outgoing side show the incoming side's frame for the first half of a cross dissolve (export frames 22 to 33 dB from the preview). Both sides are now decoded one after the other in export mode; exported frames match the preview at 47 to 56 dB across the span (`e2e/morph-cut-lib.ts` renders the same jump cut with a plain cross dissolve as a control).
- **CPU and GPU agree within tolerance.** Measured on a Chrome with a real WebGPU adapter: the displacement fields differ by 0.00001 px on average, the rendered frames by 0.002 to 0.005 levels (70 to 75 dB PSNR) on a 256x144 scene; the unit and browser tests assert the tolerance, not bit-identity.
## Immersive video (VR / 360)

- **Equirectangular only.** Projection choices are None and Equirectangular (monoscopic, stereo over/under, stereo side by side, with a captured horizontal and vertical field of view). Cubemap, equi-angular cubemap, dual-fisheye and other lens projections are neither read nor written. "Little planet" and "Fisheye" are output looks of VR Projection, not input projections.
- **Our angle conventions, not guaranteed to match Premiere's.** The picture centre is straight ahead. Rotate Sphere rotates the content (pan right moves it right, tilt up moves it up, roll turns it clockwise; applied pan, then tilt, then roll); a reframing camera is the dual (pan right looks right). A project moved to or from Premiere may need the sign of an angle flipped. The conventions are pinned by analytic tests (`vr/vr-math.test.ts`, `video/vr-effects.test.ts`).
- **Detection.** Import reads Spherical Video V2 (`st3d` / `sv3d`, equirectangular) and V1 (`uuid` XML) metadata from MP4 and MOV through the movie header (`moov`) only. WebM / MKV projection elements, XMP-only tagging and files imported through the desktop native decoder path (ProRes and other WebCodecs-undecodable codecs) are not read. A 2:1 picture without metadata is only a hint ("Looks like 360"): it is not treated as VR until you set VR Properties. Hints fire for any 2:1 picture, which includes flat 2:1 footage.
- **Effects take an explicit frame layout.** Each VR effect has its own Frame layout parameter (monoscopic by default). The agent seeds it from the sequence when a VR effect is added to a VR sequence; adding the effect from the Effects panel does not, so on a stereo sequence set the layout on the effect. Rotate Sphere, VR Blur and the second-batch effects (VR Sharpen, Glow, Chromatic Aberrations, Digital Glitch, De-Noise) process both eyes independently (no pixel crosses between the eyes; the glitch uses the same draws for both eyes so they stay coherent); VR Projection / Reframe renders from the LEFT eye only; VR Plane to Sphere has no stereo layout (it places one picture on a mono frame).
- **Single-tap sampling.** Rotate Sphere and VR Projection use one bilinear tap per output pixel (the GLSL and the CPU reference agree to 88-105 dB PSNR). There is no mip-mapping or supersampling, so a strong downscale (for example a flat view of an 8K sphere into 720p) can alias on fine detail. Pole handling is exact for Rotate Sphere (a tilt of 90 degrees puts the pole straight ahead with no hole); the poles themselves keep one row of source pixels.
- **VR Blur.** The radius is an angle (0-15 degrees) and the kernel is a golden-angle disc of at most 64 taps stretched by 1/cos(latitude) with seam wrap and reflection over the poles. Above roughly 6 degrees at 4K the disc is visibly noisy rather than smooth; it is not a Gaussian. Measured on this machine at 3840x1920 the GPU path is about 40 ms, the CPU reference (software fallback) about 40 s per frame, so without WebGL2 VR Blur needs Sequence > Render In to Out.
- **Reframe to flat draws inside the clip's own frame.** The effect cannot change the clip's frame size, so the flat view is drawn in the largest rectangle of the chosen aspect that fits the 2:1 picture and the rest is transparent. "Fill sequence with this view" (and `reframe_360_to_flat`) sets the aspect to the sequence's and the clip to Cover, which fills a flat sequence exactly; with another aspect, or a Contain fit, you see the bars. The view's resolution is that of the source frame, not of the sequence.
- **Program monitor VR view.** Program monitor, and the Source monitor has its own toggle ("VR view" in its header; independent state, it needs the clip's VR Properties from its metadata or the project panel; a 2:1 hint alone does not enable it). The Source view reads the loaded clip through a canvas of at most 2048 px wide, redrawn at up to 30 fps; the Program view reads the Program canvas, so its detail is the Preview resolution setting, and it redraws at up to 30 fps. Drag pans and tilts, the wheel changes the field of view (20-140 degrees), Reset returns to straight ahead; there is no roll, keyboard control, head-mounted display or gyro input. It is a DOM overlay: the Program frame, the scopes, the render cache and every export are unaffected (an e2e exports with the view on). A stereo sequence shows the left eye.
- **Spherical metadata on export.** A sequence with VR Properties exported to MP4 or MOV carries `st3d` (stereo mode) and `sv3d` (`svhd`, `proj`, `prhd` carrying the initial view yaw / pitch / roll as 16.16 fixed point degrees (zero when not set), `equi` with the captured-view bounds): ffprobe reports side data "Stereo 3D" and "Spherical Mapping / projection=equirectangular". The browser export adds the boxes to the muxer's trailing movie header; the desktop (ffmpeg) export patches the finished file in place, rewriting chunk offsets because ffmpeg puts the header first (the file is written next to the export and renamed over it). The Spherical Video V1 `uuid` XML (GSpherical, equirectangular, stereo mode, InitialView heading / pitch / roll, cropped-area pixels for a partial sphere) is written as the last box of the video `trak` next to V2 (ffprobe reads it back; players that read both see the same values). The initial view is set in Sequence VR Properties ("Initial view heading / pitch / roll") or by `set_sequence_vr_properties`; it is written as given, and players differ in their sign conventions for heading and pitch, so only the ffprobe round trip (yaw / pitch / roll as stored) was verified, not that a given player opens at the intended place. Not written: WebM / MKV / GIF / image sequence / MXF, ambisonic spatial-audio metadata (`SA3D`: OpenReel mixes to stereo / 5.1 and has no ambisonic audio path, so there is nothing to pass through cleanly; what an ambisonic source's channels and SA3D tag become on export was not tested), and a flat sequence is never tagged. Whether YouTube accepts the upload also depends on its own checks (resolution, aspect, codec); only ffprobe and the box layout were verified here, no upload was made.
- **Every VR effect is added neutral.** From the Effects panel or the agent a new VR Rotate Sphere has pan, tilt and roll 0, VR Projection has Projection "None", VR Blur radius 0, VR Sharpen amount 0, VR Glow brightness 0, VR Chromatic Aberrations amount 0, VR Digital Glitch intensity 0, VR De-Noise noise level 0 and VR Plane to Sphere "Place on sphere" off, so adding one changes nothing until you set a value (nothing is applied behind your back). An earlier build added Rotate Sphere at pan 30 (and the others active); effect parameters are stored in the project, so a project saved then still holds and renders those values. The effects-sweep e2e gives an effect whose defaults are neutral a non-neutral value (`proEffectActingParams`) before it asks whether the card changed the canvas.
- **VR code loads on first use.** The nine VR effects' specs, defaults and neutral values are part of the effects registry (small), but their CPU reference, GLSL and shader-uniform mapping (about 23 KB, `video/vr-runtime.ts`) are a lazy chunk, loaded by the video effects engine's async pixel pass the first time a VR effect is rendered (preview, render cache and export all go through it, so the first VR frame waits for the chunk and is never drawn without the effect) and ahead of time by the Program monitor when the project already holds one. The synchronous entry points (`applyProEffect`, `proEffectGpuUniforms`, `getProEffectShaderDef` on a VR effect) throw `VrRuntimeNotLoadedError` until it is loaded. The monitor VR view, the Source monitor VR view, the VR Properties dialog and Reframe's "Fill sequence" button are lazy components, and the Spherical Video metadata reader loads only when an MP4 / MOV is probed (the same chunk also holds the export-side box writers, loaded when a VR sequence is exported to MP4 / MOV). In the desktop build Rollup folds small side-effect-free lazy chunks into the editor chunk (`experimentalMinChunkSize`), so the dialog and overlays still ship inside it there; they are lazy components but not separate files.
- **Angle keyframes take the shorter arc.** Pan, tilt and roll (Rotate Sphere, VR Projection, VR Plane to Sphere) interpolate along the shorter way round (350 to 10 goes through 360), with the usual easing. The parameters are limited to plus or minus 360 and wrap; a spin of more than half a turn between two keyframes needs an intermediate keyframe. Other parameters interpolate linearly as before.
- **Second-batch effects (VR Sharpen, Glow, Chromatic Aberrations, Digital Glitch, De-Noise).** Same kernel family as VR Blur: golden-angle discs of at most 64 taps with an angular radius, stretched by 1/cos(latitude), seam wrap and reflection over the poles, one pass per effect (no separable or multi-pass blur, so a large glow radius is noisy rather than smooth: Glow is limited to 12 degrees and Gaussian-weighted). *Sharpen* is an unsharp mask (gain 2 at 100%) on RGB, alpha untouched. *Glow* thresholds on luminance of each tap (straight, not premultiplied colour, weighted by tap alpha), averages with a Gaussian falloff, tints and adds it; it never darkens, and it is not an HDR bloom (clamped at white). *Chromatic Aberrations* scales the angle from a centre (default straight ahead) by 1 +/- 6% x amount for red / blue; the scale fades as sin squared behind the centre so the antipode (which sits on the seam for a centre straight ahead) has no singularity, which also means the fringe is weaker than a pure lens model in the rear hemisphere. It is a look, not a model of a particular lens. *Digital Glitch* is not Premiere's block corruption: it shifts 16 bands of latitude and single rows in longitude (rotations, so neither the seam nor the poles can tear) with a red / blue split, re-rolling `rate` times a second from a hash of (seed, frame, row); the same seed and time give the same picture on the GPU, the CPU and in export, but the picture is not the same as Premiere's for the same seed. Because it is clip-time driven, a clip's glitch restarts with the clip. *De-Noise* is a spatial bilateral filter (it cannot remove noise that needs temporal averaging, and a strong setting flattens fine texture); it is not a trained denoiser. Cost at 3840x1920 on this Mac (GPU, upload + draw + read of one pixel): Sharpen 35-43 ms, Glow 45-46 ms, Chromatic Aberrations 22 ms, Digital Glitch 20-21 ms, De-Noise 42 ms; CPU reference (software fallback, no WebGL2): Sharpen 17-24 s, Glow 31-40 s, Chromatic Aberrations 3.1 s, Glitch under 0.1 s, De-Noise 18.5 s per frame, so without WebGL2 use Sequence > Render In to Out. Stacking several of the heavier ones at 4K will not play back at full rate on this machine (not measured stacked).
